# Phase 11 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Run mode:** `--auto` (non-interactive). Every value below was either pre-populated from CONTEXT.md/RESEARCH.md/ROADMAP.md or decided against direct evidence read from the existing codebase (`frontend/src/pages/ClientManagement.tsx`, `frontend/src/components/Toast.tsx`, `frontend/src/index.css`, `frontend/src/api/client.ts`). No question required a human answer. The one genuinely open item is flagged `⚠ unresolved`/`🧪 backstop` below rather than silently decided.

**Scope framing (from CONTEXT.md D-12):** this is a small, additive extension to an *existing* Upload Results modal, not a new page or a new design system. The whole surrounding frontend (`frontend/src/pages/*.tsx`) is plain React 19 with inline `style={{}}` objects and one shared `index.css` — no Tailwind, no component library, no shadcn, no icon library anywhere in `frontend/src`. Everything in this contract deliberately reuses hex values, font sizes, and layout idioms already present in that codebase rather than inventing new ones — see the shadcn gate decision immediately below.

**Primary visual anchor:** when both new sections render, the green **"Newly eligible for scheduling" callout is the primary focal point** of the modal — it is the milestone's headline win (D-14, MRG-06) and uses the only saturated block-color (success green) among the modal's new additions, while the Merge Report table stays neutral gray/white with small colored badges. Layout order follows this priority: Eligibility callout renders **first** (directly below the per-desk rollup, above the Merge Report table), so the operator's eye lands on it before scanning the denser divergence table. The Merge Report table is the secondary, reference-detail element — dense and scannable, not attention-grabbing — consistent with its role as backup evidence for what the callout already announced.

If a future phase adds a materially larger UI surface, shadcn init should be revisited then, not retrofitted here.

## Spacing Scale

Declared values (must be multiples of 4):

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Badge/pill internal vertical padding, tight inline gaps |
| sm | 8px | Compact element spacing, badge horizontal padding, list-item gaps |
| block | 12px | Block/card padding for boxed sections (Merge Report block, "Newly eligible for scheduling" callout, and the pre-existing sibling "Warnings" box and "Upload Desk Assignments" panel, `ClientManagement.tsx:345,518`) |
| md | 16px | Default block spacing, modal internal padding (existing: `padding: '1.5rem'` on the modal itself stays unchanged) |
| lg | 24px | Section padding (unused by this phase's additions — reserved) |
| xl | 32px | Layout gaps (unused by this phase's additions — reserved) |
| 2xl | 48px | Major section breaks (unused by this phase's additions — reserved) |
| 3xl | 64px | Page-level spacing (unused by this phase's additions — reserved) |

**12px is a named token (`block`), not an exception.** Verified directly against `ClientManagement.tsx:345,518`: the app's existing boxed-section convention (Upload panel, Warnings box) already uses `0.75rem`/12px block padding, not 16px or 8px. Rounding this phase's new sections to 8px or 16px would visually break alignment against those two panels that ship today, which the checker explicitly warned against. This project's spacing system therefore genuinely includes 12px alongside the 4/8/16/24/32/48/64 set — it is declared here as an intentional, permanent addition (the `block` token), not a one-off deviation. The Merge Report section and the "Newly eligible for scheduling" callout use this same `block` (12px) padding so all three boxed sections in this modal read as one family.

**Non-spacing layout exception:**
- **Modal width: 600px → ~760px.** The existing Upload Results modal is fixed at `width: '600px'` (`ClientManagement.tsx:490`). The Merge Report table needs 6 columns (Agent, Field, BambooHR value, Sheet value, Outcome) which crowds at 600px. Widen the modal's fixed width to **760px** — a content-driven adjustment to the existing modal, not a new modal, not a new breakpoint system. All other modal styling (border-radius, padding, max-height 80vh) stays unchanged. (This is a component-width value, not a spacing-scale token, so it is not part of the spacing scale table above.)

## Typography

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 13px | 600 | 1.2 |
| Heading | 14px | 600 | 1.4 |

Grounding (all four rows match existing values already in `ClientManagement.tsx`, not new sizes):
- **Body 14px/400** — table cell values (agent name, BambooHR value, sheet value), matches the dominant `fontSize: '0.85rem'` used throughout the existing modal and its sibling lists/tables.
- **Label 13px/600** — the new Outcome badges/pills, matches the existing `.desk-badge` class's `font-size: 0.8rem` (`index.css:69`).
- **Heading 14px/600** — the two new section headers ("Merge Report", "Newly eligible for scheduling"), matches the existing "Per-desk rollup" header exactly (`fontWeight: 600, fontSize: '0.85rem'`, `ClientManagement.tsx:507`) so all three sibling section headers in the modal look identical.
- **Display 18px/600** — the modal's own `<h3>Upload Results</h3>` title tier (unstyled `<h3>`, browser default ≈1.17em). Listed for completeness; this phase introduces **no new** Display-tier text — the modal title is untouched.

Only two weights are used by anything this phase adds: 400 and 600. (The surrounding file also uses 500 in a few pre-existing places — labels, primary button — those are untouched and out of this contract's scope.)

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | Unchanged. This phase adds no new primary action — the merge report is passive, read-only display (D-13: ephemeral, gone when the modal closes). The existing "Upload Desk Assignments" button (`ClientManagement.tsx:347`) is untouched. |
| Empty state heading | Not applicable — see UI Considerations "empty" rows below. When every field agrees between BambooHR and the sheet (no divergence, no gap-fill), the Merge Report section is **omitted entirely** via the same `{uploadResult.X.length > 0 && (...)}` conditional-render idiom already used for `sheetSummaries`/`warnings` (`ClientManagement.tsx:505,517`) — there is no "0 divergences" empty-table state to design. |
| Empty state body | Same as above — no separate copy needed; absence of the section *is* the empty state. |
| Error state | Reuses the existing whole-upload catch path verbatim: `showToast('error', getErrorMessage(err))` (`ClientManagement.tsx:171-172`), which already fires for any thrown error from `clientManagement.uploadDeskAssignments(file)`, including the `BambooHRRateLimitedException` → HTTP 503 `BAMBOOHR_RATE_LIMITED` MRG-07 propagates (`GlobalExceptionHandler.java:67-70`). **Copy requirement for the planner/executor:** the toast text is exactly `ex.getMessage()` from the backend exception — it must state plainly that **no changes were written**, not just that the sync failed. Required shape: `"BambooHR sync failed ({reason}) — no changes were made. Retry the upload once BambooHR is available."` Verify the backend message text meets this bar during planning; if it currently reads as a generic "rate limited" message without the "no changes were made" clause, that's a one-line message-text fix in `BambooHRRateLimitedException`/`BambooRefreshService`, not a new UI component. |
| Destructive confirmation | Not applicable — this phase adds no destructive action (REQUIREMENTS.md Out of Scope: "Editing the merged result in the UI — the spreadsheet and BambooHR remain the only input paths"). The existing "Remove agent from desk" `confirm()` dialog elsewhere in this file is untouched. |

**Merge Report section copy (new, specific):**
- Section header: `"Merge Report (N field{s} across M agent{s})"` — pluralized per the zero-one-many row below.
- Table columns, in order: `BambooHR ID | Agent | Field | BambooHR value | Sheet value | Outcome`
- Field label strings (map from D-08's contested field set): `First name`, `Last name`, `Email`, `Department`, `Job title`, `Active status`, `Working pattern (Mon–Sun)`.
- Outcome badge text: `"BambooHR override"` (spreadsheet value discarded but shown — D-07) or `"Gap-filled by spreadsheet"` (BambooHR had no data — D-06/D-08).
- Eligibility callout header: `"Newly eligible for scheduling"`, body: `"{N} agent{s} whose working pattern BambooHR doesn't know {is/are} now solver-eligible from the uploaded sheet:"` followed by a plain name list.

**Scope boundary (explicit, not decided by CONTEXT — recorded as an auto-mode assumption):** the Merge Report covers **identity fields + the whole-week working-pattern replacement** (D-05/D-06/D-07/D-08), decided and knowable at upload/merge time. It does **not** attempt to show the MRG-03/D-09 dated-vs-recurring PTO arbitration outcome, because RESEARCH.md's Pattern 4/Open Question 1 places that arbitration at **solve time** (`SolverService` day-off assembly), not upload time — the data needed to render a per-date PTO row simply doesn't exist yet when this modal renders. If planning instead resolves Open Question 1 toward merge-write-time arbitration, this scope boundary should be revisited and the report extended with PTO rows; until then, treat the Merge Report as identity + pattern only. ⚠ **This is the one point in this contract genuinely gated on an unresolved backend design decision, not a UI-only call — flagged rather than silently assumed away.**
