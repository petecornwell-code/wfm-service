store an agent's usual shift for MONDAY through a single choke-point write, read it back on the

seven export columns, and two guards against migration-vs-entity drift.

<planner_decisions>
Decisions this plan makes on the executor's behalf. Adopt them verbatim; do not re-litigate.

- **P-01 — Real FK, no denormalized name column.** RESEARCH.md Assumption A2 flags D-01's precedent
  citation as ambiguous about whether it prescribes denormalization. Ruling: real
  `@ManyToOne(fetch = LAZY)` FK to `ShiftTemplate`, no `template_name` column. `AgentShiftAssignment`
  denormalizes because it is a frozen historical record whose own service javadoc says "so history
  survives"; `AgentUsualShift` is the opposite — a live target that must always reflect current
  truth. D-01's "resolves by NAME" is satisfied by reading `stored.getShiftTemplate().getName()`
  through the FK, which is exactly what makes "Ana's usual shift is Early" follow Early.

- **P-02 — Both FKs are ON DELETE CASCADE.** `agent_day_hours.agent_id` is already
  `ON DELETE CASCADE` (V29) and `shift_template.desk_id` is already `ON DELETE CASCADE` (V39).
  `DeskService.deleteDesk` deletes the desk row and *relies* on that second cascade — a
  non-cascading `agent_usual_shift.shift_template_id` would turn every desk deletion on a desk with
  stored usual shifts into an FK violation. This is a real defect this plan prevents rather than
  introduces, and it is proven, not asserted, in Task 2.

- **P-03 — A dead template cannot be stored through the choke point.** `setUsualShift` rejects a
  `shiftTemplateId` whose era is not effective today (`isEffectiveOn(LocalDate.now())` false) with a
  400, in addition to D-03's weekday-mask rejection. D-02's "the stored row survives untouched as
  history" governs rows that were live when written and were retired later; it does not license
  deliberately writing an already-dead target. The D-17 picker only offers CURRENT eras, so this is
  the defensive server-side half of the same rule.

- **P-04 — `AgentUsualShiftPostgresTest` lives in `src/test/java/com/wfm/repository/`, not
  `com/wfm/support/`.** `16-VALIDATION.md` names the package `support`; `support` currently holds
  only the abstract base class `PostgresBackedTest`, and the only existing subclass
  (`AgentRepositoryPostgresTest`) lives in `repository`. Class name is kept exactly as VALIDATION.md
  declares it so `./gradlew test --tests AgentUsualShiftPostgresTest` still resolves.

- **P-05 — The tracer computes NOT_SET, LIVE and STORED_INACTIVE-with-reason-RETIRED.** The
  `NOT_WORKED` reason requires a cross-model read of `agent_day_hours` and is added by plan 16-02
  Task 1 together with the RETIRED-vs-NOT_WORKED precedence ruling. This is a functionality gap in
  a correct state machine, not a stub that later needs rewriting: no arm the tracer computes changes
  meaning in 16-02.

- **P-06 — the CONTROLLER composes the write and the read; `UsualShiftService` injects no other
  service.** `DeskAgentService.toResponse` is private and `DeskAgentService` has no public
  single-agent read today, so the response has to come from somewhere. The obvious move —
  `UsualShiftService` injecting `DeskAgentService` — is rejected because plan 16-02 Task 3 needs
  `DeskAgentService.removeDeskAgent` to call `UsualShiftService.clearUsualShifts`, and the two
  together would be a constructor-injection cycle Spring cannot resolve.

  Ruling: `UsualShiftService.setUsualShift(deskId, agentId, day, shiftTemplateId, clearRow)` returns
  `void` and injects only `AgentRepository`, `AgentUsualShiftRepository` and
  `ShiftTemplateRepository`. `DeskAgentService` gains a public
  `@Transactional(readOnly = true) DeskAgentResponse getDeskAgentResponse(UUID deskId, UUID agentId)`.
  `DeskAgentController.setUsualShift` calls the write, then returns the read — exactly the
  two-service composition the `refreshFromBamboo` endpoint on this same controller already uses
  (`bambooRefreshService.refreshDeskAgents(deskId)` followed by
  `deskAgentService.listDeskAgentResponses(...)`).

  Consequence: the dependency graph stays acyclic in one direction —
  `DeskAgentService -> UsualShiftService` (added in 16-02) and
  `DeskAgentService -> UsualShiftResolutionService`, with `UsualShiftService` and
  `UsualShiftResolutionService` both depending only on repositories. Because the write commits
  before the controller's read transaction opens, the response reflects the write without needing
  `setDayHours`'s explicit `flush()`-then-re-read dance; keep the `flush()` anyway so the write
  method is correct in isolation and a future in-transaction caller is not surprised.
</planner_decisions>

<assumption_delta_decision>
**Detector:** `gsd_run query assumption-delta scan "16" --json` → `detected: true`, one
`pluralization` signal on the term "second" (ROADMAP criterion 2: "not a *second*, parallel
column-layout source of truth").

**Primary noun:** *usual shift* — a per-weekday, per-agent scheduling target.

**Candidate delta:** a usual shift is a second per-weekday agent-scheduling target alongside the
existing `agent_day_hours` (contracted hours). Two instances of one shape invites promotion to a
single generalized `agent_weekday_target` table with a discriminator.

**Decision: `add-alongside`.**

**Rationale:** CONTEXT.md D-04 already rules the two models orthogonal and deliberately uncoupled —
`agent_day_hours` decides *if* the agent works, `agent_usual_shift` decides *which shift* when they
do — and the whole point of D-04 is that setting a day to MANDATORY must not have to reach into a
second table, which is exactly the cross-model write Phase 13 kept out of `setDayHours`. Two
instances is not evidence of a family; promoting now would re-couple precisely what D-04 uncoupled,
and would give the two editors a shared row shape they have no shared validation for (hours are
`NUMERIC(5,2)` with a 0–24 range rule; a usual shift is a catalog FK with a weekday-mask rule).

**What would force a later `promote`:** a *third* per-weekday agent target (e.g. a per-weekday
preferred break window, or a per-weekday specialization assignment) landing in a future milestone.
At three, the duplicated `(tenant_id, agent_id, day_of_week)` key, the triplicate desk-scoped bulk
`@Query` joining through `agent.deskId`, and the triplicate `clearDesk`/`removeDeskAgent` cleanup
call sites stop being coincidence and become a missing abstraction. Phase 17 adds no such table, so
the trigger is not in this milestone.
</assumption_delta_decision>
