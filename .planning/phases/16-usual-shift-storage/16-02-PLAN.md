<planner_decisions>
- **P-07 — RETIRED wins over NOT_WORKED when both hold.** An agent can have a stored usual shift
  whose era is retired AND whose weekday they do not work. D-16 merges both into one muted
  treatment, so the operator's next action is the same either way, but the `reason` field is a
  single value and needs a deterministic rule. Ruling: check RETIRED first. The stored reference
  itself being dead is the more fundamental fact — a template that no longer exists as a live era
  cannot be honoured on any weekday, whereas "not worked" is a per-weekday condition that could flip
  back with one hours edit. Document the precedence in `toResponse`'s code comment, not only in this
  plan.

- **P-08 — "Does not work this weekday" means: the agent has an `agent_day_hours` row for that
  weekday whose `dayOffType` is MANDATORY or PTO, OR whose `hours` has `signum() == 0`.** Use
  `signum()`, never `equals(BigDecimal.ZERO)` — the stored value is `NUMERIC(5,2)` and reads back
  scaled, so equality against an unscaled zero is false for a real stored `0.00`. A weekday with NO
  stored row is NOT "not worked": it resolves to the schedule default (a positive number), so the
  agent works it and the state stays LIVE. This mirrors `DeskAgentResponse.DayHoursEntry.hasRow`'s
  own existing distinction between an operator-set weekday and a resolved default.

- **P-09 — `deleteShiftTemplate` gains a refusal, not a cascade acceptance.** RESEARCH.md Open
  Question 2 framed this as a legibility choice (a raw `DataIntegrityViolationException` versus the
  existing `ConflictException`). Plan 16-01's P-02 `ON DELETE CASCADE` changes the stakes: without a
  guard there is no exception at all — the delete succeeds and silently destroys every referencing
  agent's stored usual shift. The guard is therefore data-loss prevention, not message polish. It
  mirrors the existing `agentShiftAssignmentRepository.countByTenantIdAndSourceTemplateId` guard
  line-for-line, including directing the caller to retire instead.

- **P-10 — `AgentUsualShiftRepository.countByShiftTemplate_Id(UUID)` is not tenant-scoped, and that
  is deliberate.** It mirrors `findByAgent_IdAndDayOfWeek` and `deleteByAgent_Id`, both of which
  take raw ids because the caller has already resolved tenant scope. `deleteShiftTemplate` resolves
  the template through `findByIdAndTenantIdAndDeskId` before calling it, so the id is already proven
  in-scope. Carry that reasoning as a comment on the method, as the sibling methods do.
</planner_decisions>

<planner_assumptions>
**FLAGGED — needs a human ruling. Edge-probe item 15 (USHF-04, category `unclassified`) stays
`unresolved`.**

The deterministic edge probe could not classify USHF-04 ("An agent with no stored usual shift is
scheduled without penalty rather than being forced toward an arbitrary default") into any of its
eight categories, and the spec-less fallback rules forbid auto-resolving an `unclassified` row with
a backstop marker or dismissing it. It is therefore surfaced here rather than silently absorbed.

**Why it resists classification, and the planner's reading:** USHF-04's operative verb is
*"scheduled"*, and nothing in Phase 16 schedules anything. This phase makes "no stored usual shift"
a first-class, representable state — `Optional.empty()` from the resolver, `NOT_SET` on the roster,
a blank export cell, no row in the table. The *penalty* half of the requirement is Phase 17's
consistency constraint (CONS-01…CONS-04), which does not exist yet. So the requirement spans two
phases and its edge shape genuinely belongs to the later one.

**What this plan does deliver against it, and what it cannot:** every truth above that mentions
USHF-04 is about representability and the absence of substitution — `resolve` returns empty, the
roster reports `NOT_SET`, no default is manufactured. What this plan cannot prove is that a solver
which does not yet read this table applies no penalty; that assertion has no code to run against.

**The assumption the planner is making, stated so it can be rejected:** that a stored state of
"absent, and distinguishable from present-but-inactive" is the complete Phase 16 half of USHF-04,
and that the penalty-free half is correctly deferred to Phase 17 where CONS-04 already requires the
consistency constraint be soft. **If the operator disagrees** — if USHF-04 is meant to be fully
discharged inside Phase 16 — this phase is under-scoped and needs a task that reads the table from
the solve path, which `16-CONTEXT.md` § Phase Boundary explicitly excludes ("This phase stores,
writes, resolves and displays. It does **not** make the solver read the value"). Raise it at verify
time rather than closing it silently either way.
</planner_assumptions>
