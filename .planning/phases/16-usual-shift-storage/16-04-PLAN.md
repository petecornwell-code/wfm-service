<objective>
Build the deliverable this phase exists for: an enumerated table of every write path that can change
agent scheduling data, one test per path that actually runs that path, and a structural guard that
fails the build when a new writer appears without a corresponding table row.

Purpose: this is the phase's named-risk repeat of v1.2 audit finding I-2 — a guarantee that held on
the upload path only, and stayed open across two consecutive audits because a second entry point
bypassed it. RESEARCH.md is explicit that there is no ready-made precedent for this guard in this
codebase and that ArchUnit is absent from `build.gradle`. Without the guard the table is true only
on ship day, which is exactly how I-2 survived.

Output: `src/test/resources/ushf-05-write-paths.md` (the canonical table, parsed by the guard),
`UsualShiftWritePathGuardTest` (the structural completeness guard), and `UsualShiftWritePathTest`
(the three paths not already exercised by earlier plans).

<planner_decisions>
- **P-16 — The guard is a static source scan (RESEARCH.md Pitfall 3 option 2), not a Spring-bean
  reflective scan (option 1).** This is the genuine design call RESEARCH.md refused to make for the
  planner, so here is the reasoning rather than a bare choice.

  *Why not option 1 (bean scan).* It is more semantically correct — it inspects the real
  dependency-injection graph rather than text — but it costs a full or sliced Spring context per
  run, and this codebase has zero precedent for it: only three test classes use `@SpringBootTest`
  and none does a bean scan. Phase 15 already recorded a live concern about the CI Test job's
  duration (`15-*/HANDOFF.md`, 12m53s), and a guard that developers are tempted to exclude for
  speed is a guard that stops existing. It also cannot see a writer that is not a Spring bean.

  *Why option 2 (source scan).* No Spring context, no container, sub-second. It matches the
  "structural-absence" idiom `DeskAssignmentUploadMultiSheetTest`'s own comment already names
  (*"mirrors plan 10-01 Task 3's structural-absence approach"*), widened from one file to a
  directory walk. Its failure modes are both acceptable: a false positive (the name appearing in a
  comment or an unrelated string) *fails safe*, forcing a human to look; a false negative would need
  a repository injected behind an abstraction that hides its concrete type, which does not occur
  anywhere in this codebase — every repository is injected by its concrete Spring Data interface
  type, confirmed across every constructor read during research.

  *Two hardenings over RESEARCH.md's sketch.* (a) Scan for TWO types, not one: the repository AND
  the `AgentUsualShift` entity, because a writer could bypass the repository entirely with
  `EntityManager.persist`. Two derivations, two expected sets — the dual-derivation shape
  `ScheduleConstraintClassificationTest` uses, adapted. (b) Derive the expected sets by parsing the
  table document rather than hard-coding them in Java, so the table is load-bearing rather than
  decorative.

- **P-17 — The canonical table lives at `src/test/resources/ushf-05-write-paths.md`, not in
  `.planning/`.** D-14 asks for "a table, plus one test per path, plus a structural completeness
  guard that fails when a new writer appears without a corresponding table row." A guard that fails
  on a missing table row has to read the table. `MigrationEntityConsistencyTest` already establishes
  the pattern of a test reading a non-Java file off the classpath. Putting the table anywhere the
  guard cannot read it would force a second hand-maintained copy inside the test — the exact
  drift-between-two-sources trap this project has named and closed twice (audit NEW-1, audit I-1).
  One file, parsed by the guard, reviewable as a document. The phase SUMMARY links to it; there is
  no `.planning/` duplicate.

- **P-18 — Two rows beyond D-14's seven, both flagged as planner additions.** Tracing the code
  surfaced two reachable paths D-14's list does not name, and XCUT-02's wording is "every guarantee
  is verified on every reachable write path, not only the one its phase built":
  *`ShiftTemplateService.deleteShiftTemplate`* — after plan 16-01's `ON DELETE CASCADE`, deleting a
  referenced template would silently remove usual-shift rows; plan 16-02 Task 1 converted that into
  a refusal, and the table records the refusal as the guarantee.
  *`DeskService.deleteDesk`* — usual-shift rows cascade away with the desk's templates; plan 16-01
  Task 2 proved it against real Postgres, and the table records the cascade as the guarantee.
  Neither is scope creep: each is one table row plus a cross-reference to a test another plan
  already wrote.

- **P-19 — The solver row is proven by an actual solve AND by the structural guard, and the solve
  reuses the cheapest existing fixture.** D-14 requires a test that exercises the path, so a
  reflection-only proof is not sufficient on its own for a path with a runnable entry point. Reuse
  an existing solve fixture rather than building a new one — `SolverServiceShiftAssignmentTest` and
  `src/test/java/com/wfm/solver/LiveShapeShiftDeskFixture.java` are the candidates to evaluate. The
  new class must add under 90 seconds to the suite; record which fixture was reused and the measured
  added runtime in the SUMMARY. If no existing fixture can be reused under that budget, report it as
  a finding rather than building a bespoke full-scale solve.
</planner_decisions>
