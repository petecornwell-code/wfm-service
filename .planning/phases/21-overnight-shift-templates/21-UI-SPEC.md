## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none |
| Icon library | none — native Unicode glyphs only (`⚠` for warnings), paired with the native HTML `title` attribute for tooltips. No icon font, SVG sprite, or icon package exists in `frontend/package.json`. |
| Font | `system-ui, -apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, sans-serif` (`frontend/src/index.css:2`) |
| Error/notification channel | `Toast` (`frontend/src/components/Toast.tsx`) — `showToast(type, text)`, global singleton, 4s auto-dismiss. Three types: `success` (green `#15803d`), `error` (red `#dc2626`), `warning` (amber `#b45309`). **This is the established channel for every existing `DeskManagement.tsx` mutation (create/update/delete)** — confirmed by reading the file; this phase extends the pattern, it does not introduce a new one. |
| Inline field-error pattern | `fieldErrorStyle = { fontSize: '0.75rem', color: '#92400e', marginTop: '2px' }`, used in `ShiftLibrary.tsx` for `400` responses carrying a field-keyed `details[]` array. **Not applicable to the day-start control** — `DeskService.setDayStart` throws single-message `IllegalArgumentException`/`ConflictException`, which the API layer maps to a bare `{code, message}` body with no `details[]` (confirmed against `DeskService.java`), so there is nothing to key a per-field block on. Toast is correct here, not a gap. |
| Tooltip pattern | native `title={...}` attribute — no tooltip library or custom component exists anywhere in `frontend/src`. |
| Disabled read-only input pattern | `<input type="..." value={v} readOnly disabled />`, precedent at `StaffingRequirements.tsx:364-368`. |

**No shadcn gate was run.** This is not a greenfield decision point: the codebase is 20+ phases deep on plain inline `style={{...}}` objects with zero component-library precedent, and the phase brief is explicit that the stack is fixed and not to be re-litigated here. Introducing a component library mid-way through a correctness-focused milestone (v1.5) would be its own, unscoped migration. Treated as equivalent to the gate's "N" branch.

## Spacing Scale

Declared values, reconciled against what `frontend/src/index.css` and the page files actually use (not the template default — this project's real scale includes 12px, which the template's default list omits):

| Token | Value | Usage |
|-------|-------|-------|
| 2xs | 4px | Icon-to-text gaps (e.g. legend swatch to label), badge internal padding |
| xs | 8px | Compact element spacing (button gaps, row action gaps) |
| sm | 12px | Table cell vertical rhythm at `0.75rem`, panel padding (`amberPanelStyle`) |
| md | 16px | Default element spacing, page padding (`.main-content`), table cell `0.75rem 1rem` |
| lg | 24px | Section-to-section gaps (`marginBottom: '1.5rem'`, `'2rem'` rounds up from here) |
| xl | 32px | Major block separation (`marginBottom: '2rem'` on allocation-grid date sections) |

48px/64px are in the template default but not observed anywhere in this codebase — do not introduce them in this phase; nothing here needs a gap that large.

Exceptions: none needed for this phase's new elements (day-start control, grid header disclosure, legend row) — all fit the scale above using values already live in the files this phase touches.

## Typography

Reconciled to exactly 4 sizes and 2 weights, matching the values already in production use in the files this phase edits (`DeskManagement.tsx`, `ScheduleResults.tsx`, `ShiftLibrary.tsx` for precedent) — not the template's placeholder defaults.

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Micro | 12px (`0.75rem`) | 400 | 1.5 (inherited from `:root`, not overridden anywhere in this codebase) |
| Label | 13px | 600 | 1.4 |
| Body | 16px | 400 | 1.5 |
| Heading | 18px | 600 | 1.5 |

Notes:
- Line-height is **truthfully 1.5 everywhere**, including headings — `index.css`'s `:root { line-height: 1.5 }` is never overridden by any `h1`/`h3`/`h4` rule in this codebase. Do not introduce a tighter heading line-height in this phase; it would be a new, undiscussed convention.
- Native, unstyled `<h1>`/`<h3>`/`<h4>` tags fall back to the browser's default bold (700) when no inline `fontWeight` is set (e.g. `DeskManagement.tsx:77,81`'s bare `<h1>`/`<h3>`). This is pre-existing inconsistency outside this phase's scope — **every new text element this phase adds must set `fontWeight` explicitly to 400 or 600**, never rely on browser-default bold, so this phase does not add a third ad hoc weight.
- Heading (18px/600) is the existing `<h3 style={{ fontSize: '18px', fontWeight: 600 }}>` pattern (`ShiftLibrary.tsx:899,1118,1124`). The allocation grid's per-date `<h4>` (D-17) currently carries no inline style at all beyond `marginBottom` — this phase's edit to it must add `fontWeight: 600` explicitly per the rule above, not inherit browser bold.

## Copywriting Contract

| Element | Copy |
|---------|------|
| Primary CTA | **No new CTA.** The day-start control is edited inline within `DeskManagement.tsx`'s existing per-row edit mode; it is submitted by the existing "Save" button already in that row. Do not add a second save action scoped to just this field. |
| Day-start save refusal — sub-minute precision | Toast (`error`): backend message verbatim — `"Desk day start {value} must not carry seconds or sub-second precision"`. Reachable only via manual keyboard entry bypassing the `<input type="time" step="900">` picker UI; still wired for defense in depth. |
| Day-start save refusal — non-15-minute boundary | Toast (`error`): backend message verbatim — `"Desk day start {value} is not a 15-minute boundary"`. Same defense-in-depth note as above — `step="900"` on the picker makes this normally unreachable from the UI. |
| Day-start save refusal — ACCEPTED schedule exists (race path) | Toast (`error`): backend message verbatim — `"Desk has an accepted schedule ({scheduleId}) with period {periodStart}–{periodEnd}"` (exact interpolation per `DeskService.setDayStart`'s existing `ConflictException` text). Fires only on a stale page or a concurrent accept racing the edit — the primary case is prevented by D-04's disabled rendering below. |
| Day-start generation-time refusal (`requireDayStartTiles`) | **Not surfaced by this control.** Fires later, on the timeslot-generation screen, through that screen's own pre-existing Toast wiring. This phase does not touch that surface — only D-05's proactive warning below, which exists so the operator learns about the mismatch before reaching that screen. |
| D-05 tiling warning (non-blocking) | Toast (`warning`): `"Day start {value} will not tile cleanly with this desk's existing {incrementMinutes}-minute timeslots — regenerating will leave a partial slot at the boundary. The desk still saved."` Fires after a successful save (the save is never blocked), only when the desk has at least one live generated timeslot (`getLiveBounds` returns non-null) and `{value} % incrementMinutes != 0`. |
| D-05 tiling warning — empty case | **No warning, no banner.** A desk with zero generated timeslots has no increment to compare against — `getLiveBounds` returns null/empty — so the check silently does not fire. This is correct behaviour, not a missing state: do not render a placeholder ("no data to check") message, which would read as an error where none exists. |
| D-04 disabled-control explanation | Inline text directly beneath the (now `readOnly disabled`) day-start input, muted (`#6b7280`, 13px): `"Locked — accepted schedule blocks day start. {scheduleId} ({periodStart}–{periodEnd})."` Requires the `Desk` response to carry the blocking schedule's id and period (not present on the DTO today — flagged for the planner as a required backend addition, not a UI-only change). |
| D-04 error path (stale/concurrent) | Same Toast (`error`) row as the "ACCEPTED schedule exists" refusal above — this is the belt-and-suspenders case where the disabled-render check and the server check disagree (page was stale, or another operator accepted a schedule in the intervening moment). |
| D-02 refusal on a `00:00` desk | Replaces `"Shift template end time must be after its start time"` with: `"Shift template end time must be after its start time — this desk's business day starts at {dayStart}, so {startTime}–{endTime} would span two business days. Give the desk an overnight day start to allow this."` Names the desk's actual day start so the operator is pointed at the real cause (the anchor), not their own times. |
| Excel legend — new row (D-12, locked verbatim) | `"Sun 22:00-Mon 06:00    shift crossing into the next calendar day"` — exact text from CONTEXT.md D-12, reproduced here as the contract. Do not reword. |
| Allocation-grid section header disclosure (D-17) | `<h4>` text becomes `"{date} (business day: {startAbbrev} {dayStart}–{endAbbrev} {dayStart})"`, e.g. `"2026-09-27 (business day: Sun 21:00–Mon 21:00)"`. Suppressed entirely at a `00:00` anchor (renders bare `{date}`, byte-identical to today). Mirrors D-12's compact `Abbrev HH:MM-Abbrev HH:MM` form (no spaces around the dash) for one disclosure convention across the export and the screen; wraps it in a parenthetical `"(business day: ...)"` label because, unlike D-12's shift cell, the reader has no other cue that a span is being disclosed here. |
| Destructive confirmation | **None new in this phase.** The existing `confirm('Delete this desk and all its data?')` flow (`DeskManagement.tsx:40`) is unchanged. Changing a desk's day start is a *refusal* (D-03/D-04), never a silent destructive action, so no new confirm dialog is introduced — consistent with this project's existing bias against `confirm()` on non-destructive actions (Phase 14 D-12). |

## UI Considerations

Applicable state considerations resolved: 9 covered, 2 backstop, 0 unresolved.

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Day-start control's D-05 tiling-warning check | ✅ covered | A desk with zero generated timeslots has nothing to compare against; the check silently does not fire — no banner, no copy. See Copywriting Contract row "D-05 tiling warning — empty case." |
| loading | Day-start control, in-flight save | ✅ covered | Reuses the existing per-row `editingId`/Save-button pattern already in `DeskManagement.tsx` — the Save button disables for the duration of the request (`DeskAgents.tsx`'s `disabled={savingCell}` precedent). No spinner: this codebase reserves the spinner (`ScheduleResults.tsx:246`) for actual multi-second solver runs, not sub-second field saves. |
| error | Day-start control, all 3 UI-reachable save refusals + the race-path refusal | ✅ covered | All four route through `Toast('error', getErrorMessage(err))`, the file's existing error channel — see Copywriting Contract rows above. |
| error | Day-start control, disabled-but-stale race | ✅ covered | D-04's disabled render is the primary guard; the server's own refusal is the backstop if the page was stale. Same Toast row. |
| populated | Day-start control, normal value display (read mode and edit mode) | ✅ covered | Read mode keeps today's plain-text cell format (`{desk.dayStart}`); edit mode becomes `<input type="time" step="900" value={...}>`. No new states beyond disabled/enabled. |
| long-text / overflow | Excel Roster cell, overnight shift text | ✅ covered | D-12 is the locked, pre-selected resolution: column width rises from `16*256` to `22*256` POI units (19-character string `"Sun 22:00-Mon 06:00"` plus 3 chars padding), same-day cells byte-identical, no truncation needed at that width. |
| long-text / overflow | Allocation-grid `<h4>` header, span-disclosure text added | 🧪 backstop | The added parenthetical is short and fixed-format (`" (business day: Sun 21:00–Mon 21:00)"`, ~37 chars) and this codebase has no responsive breakpoint logic to test against — held out as a manual visual check at a 21:00-anchored desk rather than an automated assertion, since there is no frontend test runner (D-15) to wire a real one. |
| zero-one-many | Allocation grid, overnight shifts within a business-day section | ✅ covered | D-16's anchored ordering is unconditional across both render branches regardless of how many (zero, one, or many) overnight shifts exist on a given business day — there is no separate "overnight shift present" branch to get this wrong in. |
| partial | Day-start control mid-typing (a 4-digit partial time before the picker commits) | ✅ covered | Native `<input type="time">` only ever emits a complete `HH:MM` value or an empty string to `onChange` — there is no partial/malformed intermediate state to design for; this is a browser-native guarantee, not application code. |
| nav / loading | Allocation grid's two-speed polling (summary every 2s, detail every 30s) | ✅ covered | Pre-existing, unchanged by this phase (`ScheduleResults.tsx`'s documented two-speed polling comment). Flagged here only to confirm this phase's new fields (`dayStart` on `ScheduleDetailResponse`/`ScheduleSummary`, D-15) ride the existing polling cadence rather than adding a new fetch. |
| error | D-14's structured violation DTO fields vs. the two label-parsing consumers | 🧪 backstop | Out of this UI-SPEC's assigned scope (not one of the four copy items the phase brief named), but flagged because it shares the same surface: if the DTO fields land without both parsers (`ScheduleExportService:832-837`, `ScheduleResults.tsx:391`) being re-pointed in the same commit, unfilled-seat counts silently misattribute. No frontend test runner exists to assert this automatically — held out as a manual cross-check (export one overnight-shift schedule, confirm unfilled counts land on the correct date in both the UI and the Excel export) rather than an automated test. |
