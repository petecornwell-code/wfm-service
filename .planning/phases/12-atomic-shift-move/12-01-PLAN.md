<objective>
Prove the atomic shift move end-to-end on the thinnest possible path: one under-hours
agent-day, one legal shift window, one composite move, executed inside a real local search
under `EnvironmentMode.FULL_ASSERT`, with the new move factory composed alongside — not
replacing — the existing change/swap selectors.

Purpose: the two riskiest unknowns in this phase are (a) whether a hand-written move survives
Timefold's auto-generated undo without corrupting the incremental score, and (b) whether adding
an explicit `moveSelector` silently deletes today's fine-grained repair. Both are architectural
dead-ends if wrong, and both are cheap to discover now and expensive to discover after the
window-search breadth, move-pool bounding and benchmark harness are built on top. This plan
answers both before any expansion work starts.

Output: `ShiftWindowFinder`, `AssignSeatMove`, `AtomicShiftMoveFactory`, the rewritten
`<localSearch>` block in `solverConfig.xml`, `AtomicShiftMoveFullAssertTest`, and a corrected
Timefold version line in `.planning/STATE.md`.

receives a complete contracted shift — contiguous work slots plus exactly one legally positioned
break gap — placed by a single composite move, executed inside a real local search. Breadth

1. Create `src/main/java/com/wfm/solver/ShiftWindowFinder.java` in package `com.wfm.solver`,
   wildcard-importing `com.wfm.model.*` per the package convention. It must remain a plain Java
   class with zero Timefold API imports so it is unit-testable without a solver. Public static
   methods, each mirroring the constraint provider's arithmetic exactly rather than re-deriving
   equivalent-looking maths:
   - `requiredWorkSlots(AgentDayConfig)` — `effectiveHours * 60 / incrementMinutes` using
     `RoundingMode.HALF_UP`, identical to `ScheduleConstraintProvider.expectedWorkSlots`
     (line 515).
   - `breakThresholdSlots(AgentDayConfig)` — `breakMinShiftHours * 60 / incrementMinutes` using
     `RoundingMode.CEILING`, identical to the threshold calculation inside `exactlyOneBreak`
     (line 164). These two rounding modes are genuinely different and both are required; do not
     unify them.
   - `breakSlotCount(AgentDayConfig)` — integer `breakDurationMinutes / incrementMinutes`.
   - `needsBreak(AgentDayConfig)` — `effectiveHours.compareTo(breakMinShiftHours) > 0`.
   - `isAligned(LocalTime, BreakAlignment)` — the same three-branch switch as
     `ScheduleConstraintProvider.isAligned` (line 595): ON_HOUR minute==0, ON_HALF_HOUR minute is
     0 or 30, ON_QUARTER_HOUR minute % 15 == 0.
   - `findWindows(List<AgentAssignment> candidateSeats, AgentDayConfig dayConfig)` returning
     `List<ShiftWindow>`, where `ShiftWindow` is a nested public record
     `ShiftWindow(List<AgentAssignment> workSeats, LocalTime breakStart)` and `breakStart` is null
     when no break is required. In THIS task the method returns at most one element — the earliest
     legal window. The signature stays list-returning so 12-02 broadens the enumeration without
     an API change.

   Window geometry: index `candidateSeats` by `getTimeslot().getStartTime()`, keeping exactly one
   seat per distinct start time so a window can never violate `oneAssignmentPerTimeslot`. Walk
   consecutive start times stepping by `incrementMinutes`. A candidate span is
   `requiredWorkSlots + breakSlotCount` consecutive present start times when a break is required,
   or `requiredWorkSlots` consecutive start times when it is not. For a break-requiring span
   beginning at `spanStart`, try break offsets k from 1 to `requiredWorkSlots - 1`; compute
   `breakStart = spanStart + k * incrementMinutes`,
   `breakEnd = breakStart + breakSlotCount * incrementMinutes`,
   `shiftEnd = spanStart + (requiredWorkSlots + breakSlotCount) * incrementMinutes`, and
   `blockedMinutes = breakBlockedHours * 60`. Accept the offset only when all three hold:
   `isAligned(breakStart, breakStartAlignment)`; `breakStart` is not before
   `spanStart.plusMinutes(blockedMinutes)`; `breakEnd` is not after
   `shiftEnd.minusMinutes(blockedMinutes)`. This reproduces `breakBlockedWindow` (lines 225-257)
   and `breakStartAlignment` (lines 265-287) so the generated state is one the HARD constraints
   accept in a single step. `workSeats` for the accepted window are the span's seats minus the
   `breakSlotCount` seats occupying the break slots.

   `AbstractMove.doMoveOnly` already does. Do NOT construct Timefold's internal `ChangeMove`; its
