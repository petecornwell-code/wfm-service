coverage validator, leaves the way out open, refuses while a solve is running, and provably never
touches an accepted schedule.

`schedulingMode` on every desk response.

<planner_decisions>
- **P-21 — D-13's 409 is `ConflictException` reading `InMemoryScheduleStore`, not a new exception plus a
  new map.** 14-RESEARCH.md Pitfall 1 and 14-PATTERNS.md both flag this as a genuine plan-time choice and
  refuse to make it. Resolved here: D-13's text names the *idiom* — a per-desk in-flight check producing
  409 — not literally the `RefreshInProgressException` class. `BambooRefreshService` needs its own
  `ConcurrentHashMap` because nothing else knows a refresh is running; the mode switch does not, because
  `InMemoryScheduleStore` already holds exactly that fact and `DeskService` already injects it (verified:
  `DeskService` constructor parameter 11, used at `deleteDesk`). `ConflictException` already maps to 409
  `CONFLICT` in `GlobalExceptionHandler`. So: zero new exception class, zero new map, zero new handler
  mapping, zero duplicated state. The frontend branches on `ApiRequestError.status === 409`, which it
  already exposes, rather than on a bespoke code — 14-UI-SPEC.md §5's toast copy works with either.
- **P-22 — The RUNNING guard applies in BOTH directions; the coverage gate applies only SLOT to SHIFT.**
  D-12's "ungated" is about the *validation* gate — the slot model has no library prerequisite — and its
  stated purpose is keeping the fallback takeable. D-13's stated purpose is different: preventing an
  unauditable state where a schedule produced under one model is accepted into a desk flagged as the
  other. That hazard is symmetric, so the 409 guard is symmetric. Recorded explicitly because the two
  decisions read as if they conflict and a later reader will ask.
- **P-23 — Switching to the current mode is an early-return no-op.** No guard, no validation, no write,
  no refusal. There is nothing to gate when nothing changes, and refusing an idempotent request would
  make the UI's optimistic toggle behave surprisingly on a double click.
- **P-24 — Guard first, then validate, then write, all in one `@Transactional` method.** The 409 is the
  cheaper and more specific refusal, so it is evaluated first. The `InMemoryScheduleStore` read sits
  immediately before the `deskRepository.save`, with no I/O between them, which is the narrowest window
  available without introducing a lock spanning the solver and the desk table. This is a narrowed window,
  not an eliminated race — recorded honestly in the threat register rather than claimed as atomic.
- **P-25 — `DeskResponse` gains `schedulingMode` as a trailing component.** Only `DeskController`
  constructs it (verified: no other production or test file references the record), so extending it is a
  one-site change. Appending rather than inserting keeps the existing positional order intact.
</planner_decisions>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → `PUT /api/v1/desks/{deskId}/scheduling-mode` | An untrusted `deskId` and an untrusted mode value cross here |
| `X-Tenant-ID` → `TenantContext` | Tenant identity, enforced in application code only — no DB row security |
