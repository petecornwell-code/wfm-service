<objective>
An operator can ask a desk for a suggested shift library computed from its staffing demand and its
agents' effective contracted hours, and receives an editable draft that is never applied
automatically.

Purpose: composing a library by hand is the slow, error-prone step that keeps desks on slot mode.
The ROADMAP pulled SHLB-07 forward specifically so its effects are testable immediately, without
waiting for the envelope work — this plan is that immediacy, and it is deliberately not solver work.

Output: a stateless `GET .../shift-library/suggestion` endpoint returning draft rows plus, when
demand cannot be fully covered, the still-uncovered windows in the shape the coverage report
already emits.
</objective>

<planner_decisions>
- **P-08 — candidate enumeration is bounded by the desk's own grid, and the bound is named.** The
  ROADMAP is explicit that the candidate set is tens, not thousands, and that generation "must not
  acquire its own quality-plateau argument". Enumerate span starts on the desk's live timeslot grid
  between the earliest and latest demanded times; enumerate span lengths as the distinct contracted-
  hours values present in `agent_day_hours` for the desk, each plus each candidate break duration;
  enumerate band offsets on the same grid increment inside the span. Apply a hard cap on the
  generated candidate count; exceeding it is a named refusal, not a silent truncation, so a desk
  whose data shape breaks the ROADMAP's sizing assumption says so out loud instead of quietly
  returning a worse answer.
- **P-09 — cover method: greedy, then exactly verified.** Pick the candidate covering the most
  still-uncovered demand windows, repeat until nothing improves, then verify the resulting draft
  through the same `covers()` predicate the validator uses. Ties broken by the D-10 deterministic
  rule (fewest total envelope-hours beyond demand, then earliest span start, then shortest span,
  then smallest first band offset) so the same demand always produces the same draft. No new
  dependency, no ILP, no second Timefold model — RESEARCH.md § Alternatives Considered rejects all
  three for this candidate-set size.
- **P-10 — generated names and dates.** `Suggested 1`, `Suggested 2`, … in emission order;
  `effectiveFrom` = today; `effectiveTo` = null (open-ended) — mirroring the manual Add form's own
  defaults so nothing about a generated row's starting state looks unfamiliar. Every field is
  editable before save; the name is a placeholder that visibly invites rename.
- **P-11 — capacity is emitted blank on every generated band** (D-03: the editor and generation both
  default it blank, so nobody creates an infeasible library by accident).
</planner_decisions>

Create `ShiftLibraryGenerationService` as a plain `@Service` with `final` constructor-injected
collaborators (`StaffingRequirementRepository`, `AgentDayHoursRepository`,
`TimeslotGeneratorService`, `ShiftLibraryValidationService`) and no Lombok, resolving
`TenantContext.getTenantId()` at the top of its one public method — never a caller-supplied tenant,
the T-14-15 convention every service in this package follows.

The public method takes a `deskId` and returns a `ShiftLibrarySuggestionResponse`. It performs no
write of any kind: no repository `save`, no `EntityManager` use, no persistence call anywhere in the
class or its collaborator calls. This is the whole of D-11's mitigation for threat T-15-07 and is
stated as a prohibition on this plan — the class must be readable as obviously side-effect-free.

Load live demand through `staffingRequirementRepository.findAllLiveByDesk(tenantId, deskId)`
filtered to `requiredFTEs > 0` — the exact demand definition `ShiftLibraryValidationService.validate`
already uses, so a window generation calls covered is a window the validator calls covered. Load the
desk's live grid bounds through `timeslotGeneratorService.getLiveBounds(deskId)`. Load contracted
hours through `agentDayHoursRepository.findByTenantIdAndDeskId(tenantId, deskId)` and reduce to the
distinct set of hours values per weekday.

Enumerate candidates per P-08: span starts stepping the grid increment from the earliest demanded
start to the latest demanded start; for each distinct contracted-hours value present on the demanded
weekdays and each candidate break duration drawn from the grid increment's multiples up to the
desk's configured break duration, a span length of that net duration plus that break duration; band
offsets stepping the grid increment strictly inside the span. Emit each candidate as a template
carrying one or more bands rather than as an overlapping pair — a single template with two bands
self-covers its own break hour under D-02's any-band coverage, which is precisely why the band
schema ships ahead of generation (D-09). Filter candidates by the exact contracted-hours match:
a candidate is admissible only when at least one of its bands yields a net duration that equals some
agent's `AgentDayHours` value for that weekday, compared through the same
`BigDecimals.normalize(...).compareTo(...)` exact equality the validator uses. Hours matching is a
filter on candidates, never an objective (D-10). Drop any candidate whose band boundaries would not
be grid-aligned, so nothing is proposed that `ShiftTemplateService.validateGridAlignment` would then
reject.

Run the greedy-then-verify cover of P-09, minimising template count with total envelope-hours beyond
demand as the deterministic tiebreak, then re-verify the assembled draft window by window through
`ShiftLibraryValidationService`'s public coverage wrapper — not a re-derivation of the same logic.
A draft that fails its own verification is a bug, not a partial result; assert it rather than
returning it silently.

Define `ShiftLibrarySuggestionResponse` as a record carrying `List<SuggestedTemplate> templates` and
`List<ErrorResponse.ErrorDetail> uncoveredWindows`, where `SuggestedTemplate` is a nested record of
`String name, LocalTime startTime, LocalTime endTime, List<SuggestedBand> bands,
List<DayOfWeek> validWeekdays, LocalDate effectiveFrom, LocalDate effectiveTo, BigDecimal netHours`
and `SuggestedBand` is `int offsetMinutes, int durationMinutes, Integer capacity`. The shape
deliberately mirrors `ShiftTemplateRequest`'s field set so the frontend can hand a draft row
straight to the existing create endpoint without a translation layer. Names follow P-10, capacity is
always null per P-11.

Add `GET /suggestion` to `ShiftLibraryValidationController` (already mapped at
`/api/v1/desks/{deskId}/shift-library`), so the suggestion sits beside the validation report an
operator reads. The handler delegates and returns the response; it declares no request body and
performs no write.

Write `ShiftLibraryGenerationServiceTest`'s first case: seed a desk with a full week of live demand
across an 08:00–21:00 grid and agents contracted 8h, request a suggestion, and assert the returned
draft's templates, fed back through `ShiftLibraryValidationService.validate`, report zero uncovered
windows — the requirement's own acceptance criterion. Assert the draft contains banded templates
(at least one template with more than one band, or a template whose single band's break hour is
covered by another template) rather than a set of break-less envelopes.

Implement D-12's two non-happy outcomes.

**Partial coverage.** When the greedy cover cannot reach every demand window, return the best
partial draft *plus* the still-uncovered windows, each as an `ErrorResponse.ErrorDetail` with field
`"coverage"`, the message being the window rendered exactly as
`ShiftLibraryValidationService.findUncoveredWindows` renders it (date, space, start, hyphen, end),
and a null value — byte-identical to what `requireShiftModeReady` already emits for the same finding.
This is the concrete meaning of "the panel an operator reads after generating is the panel they read
after validating": the frontend reuses `CoveragePanel` unmodified. Do not refuse outright when full
coverage is impossible — the desk that most needs help would get nothing. Do not relax the
contracted-hours filter to force full coverage — that would emit exactly the templates that make the
envelope and contracted-hours constraints jointly unsatisfiable, the failure ARCHITECTURE.md § 1
names.

**Refusal.** A desk with zero live demand rows, or zero agents carrying contracted hours, is refused
and never handed an empty draft — D-05's never-pass-vacuously rule. Throw
`PreSolveValidationException` with a single `ErrorDetail`, reusing
`ShiftLibraryValidationService.NO_DEMAND_MESSAGE`'s diagnostic clause byte-identically ("This desk
has no staffing demand loaded.") and adapting only the trailing call-to-action clause to the
generation context, per the UI-SPEC copywriting contract. One shared message covers both trigger
conditions — the phase deliberately does not distinguish which precondition failed, mirroring the
fact that the underlying guard is one guard, not two. `PreSolveValidationException` already maps to
400 `VALIDATION_FAILED` with a populated `details` array through `GlobalExceptionHandler`, so no new
exception type and no new handler mapping is introduced.

**The candidate-cap refusal (P-08).** If enumeration exceeds the declared candidate cap, throw the
same exception type with a distinct `ErrorDetail` naming the cap and the count, so a desk whose data
shape breaks the ROADMAP's tens-not-thousands sizing assumption is told so rather than silently
handed a truncated search.

rendering of those windows character for character; a desk with demand but no contracted-hours
agents, asserting the refusal; a desk with contracted-hours agents but no live demand, asserting the
same refusal message; and a desk with demand rows all at `requiredFTEs = 0`, asserting the refusal
(a zero-FTE row is not demand).

  <name>Task 3: Determinism, minimality, and the break-less-template prohibition</name>
  <files>src/main/java/com/wfm/service/ShiftLibraryGenerationService.java, src/test/java/com/wfm/service/ShiftLibraryGenerationServiceTest.java</files>
  <action>
Make the deterministic tiebreak of P-09 explicit and testable. Enumeration and the greedy selection
must both iterate over stably ordered collections — sort candidates by span start ascending, then
span length ascending, then first band offset ascending, before the cover loop begins, and sort each
template's bands offset-ascending on emission. A `HashSet` or `HashMap` iteration order anywhere in
the selection path is a defect: the same demand must produce the same draft on every JVM run,
because XCUT-04's seeded benchmark cannot reproduce across runs if the library it starts from varies.

Enforce the break-less-template prohibition recorded on this plan. A candidate whose band list is
empty is admissible only when its net working duration is strictly below the desk's
`breakMinShiftHours` — the threshold the schedule config already carries and the four break
constraints already read. A full-length break-less shift is never generated. Zero bands remains a
valid state an operator may choose deliberately for a short shift (D-08 discretion, preserved), but
it is not something generation proposes for a shift long enough that the desk's own configuration
says a break is required. Reject such a candidate during enumeration rather than filtering it later,
so the prohibition holds by construction.

Extend the test with three cases: request a suggestion twice against an unchanged fixture and assert
the two responses are equal field for field, including band order within each template; assert the
returned template count is not larger than a hand-built cover of the same demand (minimality — D-10's
objective), using a fixture whose optimal cover size is known by construction; and assert that no
returned template has an empty band list when its net duration reaches the fixture's
`breakMinShiftHours`, with a companion case at a shorter duration where a break-less template is
permitted.
