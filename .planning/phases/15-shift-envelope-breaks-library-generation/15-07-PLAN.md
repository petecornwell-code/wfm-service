<planner_decisions>
- **P-30 — the accepted row denormalises; it does not copy a template.** `acceptSchedule`'s existing
  pattern copies live `Timeslot` and `StaffingRequirement` rows into schedule-scoped copies with FKs
  remapped. D-07 deliberately deviates: copying a template plus N band rows per accepted schedule to
  record one envelope per agent-day is a lot of rows to record one fact, and an FK to the live
  template is unsafe because `updateShiftTemplate` can mutate times — a routine correction would
  silently rewrite what history says an agent worked. Mirror the *control flow* of the existing
  snapshot block (build a new row, set tenant/desk/schedule, persist through the entity manager), not
  its copy-the-whole-entity field shape.
- **P-31 — grouping is keyed by template identity, not by envelope times.** Two templates with the
  same start and end but different ids (a different name, or a different era) are two groups. Key on
  the accepted row's `sourceTemplateId` when present and fall back to the template name, so the key
  survives a null lineage id.
- **P-32 — `schedulingMode` on `ScheduleDetailResponse` records the mode the schedule was solved
  under**, not a live re-fetch of the desk's current mode. A report must render correctly even if the
  desk's mode changed after this schedule was accepted — consistent with MODE-04's round-trip
  guarantee, which Phase 14 proved field by field across SLOT→SHIFT→SLOT against an accepted schedule.
- **P-33 — the frontend branches at the top of the per-date block**, mirroring the backend's own
  mode-gating discipline for the identical reason: a shift-mode change must not be able to leak into
  slot-mode rendering by construction. `if (schedulingMode !== 'SHIFT')` renders the existing table
  untouched; `else` renders the grouped variant.
</planner_decisions>
