## P-01 — The configured-or-not signal is the snapshotted value itself, not the counts' presence

22-VERIFICATION.md's `missing:` item 2 offers two routes. This plan takes **both halves of the
stronger one**: the detail response gains the counts *and* gains `minimumRestMinutes`, and the
frontend gate is re-pointed at `minimumRestMinutes`.

Adding only the counts would technically satisfy the letter of the item — the detail response would
then carry them itself, so the full-replace wipe becomes harmless. It is rejected because it leaves
the proxy in place. `22-UI-SPEC.md` specifies the gate twice, verbatim, as **"the schedule's
snapshotted `minimumRestMinutes`"** (E4/empty, and §3(a) of the Surface-by-Surface contract). Plan
22-10 substituted "both counts are present" for it and said so in its own code comment — "there is
no separate snapshotted-minimum-rest field on either DTO". That substitution is what made the
surface silently lie, because a count can be absent for a reason other than "rest is not
configured". Adding the real field restores the UI-SPEC's literal wording and removes the class of
defect rather than one instance of it.

**UI-SPEC divergence introduced: none.** This change makes the code agree with the UI-SPEC's
wording for the first time. What becomes stale is the *code's own comments* in
`ScheduleResults.tsx` (the badge comment and `RestWaiversTab`'s header comment both assert "there
is no separate snapshotted-minimum-rest field on either DTO"), and Task 1 rewrites them. No
UI-SPEC edit is required.

**Reversibility: `reversible`.** Three additive, nullable DTO fields and one changed gate
expression. No schema change, no migration, no persisted state — undo is deleting the fields. No
`checkpoint:decision` is required for this plan. (The one route in this gap closure that *would*
have been `one-way` — persisting the counts at accept time behind a Flyway migration — is rejected
in `22-12-PLAN.md`'s P-02, where the cost argument lives.)

## P-02 — `ScheduleSummary` does NOT gain a `minimumRestMinutes` component

Deliberate exclusion, recorded rather than dropped. The summary's two counts become genuinely
truthful in 22-12, so the summary needs no second signal; and the only frontend consumer of those
counts is `ScheduleResults.tsx`, which always loads the detail response before any poll begins
(`loadDetail(true)` runs first in the effect, and `tickSummary` is started only from its `.then`).
So the gate is always fed. Adding a redundant component to a record with a construction site and a
parity test would be churn with no consumer.
</planner_decisions>
