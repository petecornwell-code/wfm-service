- **P-09 — The anchored function set and its names (CONTEXT.md Claude's Discretion on D-19/D-20).**
  Five additive public statics, each named so the two arithmetic vocabularies are impossible to confuse
  at a call site, which is what D-19 asks for while both vocabularies coexist:

  | Function | Returns | Range | Counterpart |
  |---|---|---|---|
  | `startMinuteFromDayStart(LocalTime dayStart, LocalTime start)` | `int` | `[0, 1440)` | `startMinute` |
  | `endMinuteFromDayStart(LocalTime dayStart, LocalTime end)` | `int` | `(0, 1440]` | `endMinute` |
  | `timeAtDayStartOffset(LocalTime dayStart, int minutesFromDayStart)` | `LocalTime` | accepts `[0, 1440]` | `toLocalTime` |
  | `businessDateOf(LocalTime dayStart, LocalDate calendarDate, LocalTime timeOfDay)` | `LocalDate` | — | new concept (D-20) |
  | `calendarDateAtDayStartOffset(LocalTime dayStart, LocalDate businessDate, int minutesFromDayStart)` | `LocalDate` | accepts `[0, 1440)` | new concept |

  The `...FromDayStart` / `...AtDayStartOffset` suffixes are the visual distinction; a section banner
  comment separates the two blocks inside the class. The `00:00`-in-an-END-position convention
  generalises exactly: `endMinuteFromDayStart(21:00, 21:00)` is 1440 (the end of a 21:00-anchored
  business day) and `endMinuteFromDayStart(21:00, 00:00)` is 180, so the existing rule survives
  unchanged rather than being special-cased.

- **P-10 — The generation walk iterates business dates and derives calendar dates, not the reverse.**
  D-22 makes `periodStart`/`periodEnd` business dates, so the outer loop cursor is named
  `businessDate` and each slot's calendar date is derived from the anchor plus the slot's offset. The
  alternative — iterate calendar dates and derive a business date per slot — reproduces the
  calendar-dates-with-clipping shape D-22 explicitly rejects, because it manufactures partial business
  days at both period edges. `businessDateOf` still has a real second caller: `isDesired` classifies an
  *existing* row, which carries only a calendar date and a start time.

- **P-11 — `isDesired` derives the business date; it never reads the stored column.** D-22 requires
  `isDesired` to partition on business date; D-12 requires that nothing reads `timeslot.business_date`
  in this phase. Both hold if `isDesired` takes the desk anchor and the row's calendar date and calls
  `businessDateOf`. `isDesired`'s first parameter becomes `dayStart`; its second stays the row's
  calendar date, so the call site changes by one argument, not by a field access.

- **P-12 — The closing read-back widens its calendar window by one day and filters on the derived
  business date.** `generateTimeslots` returns rows fetched by a calendar-date `BETWEEN`. Under D-22
  those bounds are business dates, so for a 21:00-anchored desk the last business day's post-midnight
  rows sit on calendar `periodEnd + 1` and would be silently dropped — a silent under-return of exactly
  the shape REQUIREMENTS.md names as this milestone's characteristic failure. The fix uses the existing
  finder with an upper bound of `periodEnd.plusDays(1)` and then filters and orders in memory by
  derived business date and offset-from-day-start. At a `00:00` anchor the widened query pulls in the
  following calendar day's rows and the filter removes every one of them, so the returned list is
  identical to today's, in the same order. No new repository method.

- **P-13 — D-21 is in THIS phase, and RESEARCH.md's note to the contrary is wrong.** RESEARCH.md's
  "State of the Art" section says the `@Deprecated` annotations are "new in Phase 19, not this phase".
  CONTEXT.md D-21 is the binding contract and says the opposite, and its own rationale settles it: the
  annotations exist to replace the roadmap's *Phase 19 planning-time* re-grep action item with
  something that cannot go stale, which only works if they land before Phase 19 is planned, and D-21
  explicitly "accepts a noisy build for one phase" — this phase. All nine current midnight-implicit
  statics are annotated, because Phase 19's own success criterion is that every call site supplies an
  explicit day start.

- **P-14 — `-Xlint:deprecation` is added so D-21's "live count" is real.** Without it javac emits one
  aggregate note per compilation unit instead of a warning per call site, and D-21's stated purpose —
  the compiler enumerating what Phase 19 must re-point — is only half delivered. A single
  `tasks.withType(JavaCompile)` block adds the flag. No `-Werror` is added and none exists, so the flag
  cannot fail a build; the cost is exactly the noise D-21 accepts. Pre-existing deprecation warnings
  from Spring or Timefold surfacing alongside is expected and is not a defect to chase in this phase.

- **P-15 — Line-number citations come from RESEARCH.md, not CONTEXT.md.** RESEARCH.md Pitfall 1
  verified that CONTEXT.md's `DayWindow` citations drifted: the class javadoc's statement of the

  the method declared at line 73, and `toLocalTime`'s range throw is lines 123-125. Read the file rather
  than trusting any of these numbers.
