assertion.

same resource, and a pipeline-level red-proof against a synthetic offender.

<planner_decisions>
- **P-26 — Wave 3, after every plan that touches `src/main`.** The comparison allowlist is set-equal to
  what the scan finds in `src/main/java`, so its contents are a function of the finished tree. This is a
  real coupling that no file overlap expresses: plans 18-02 and 18-03 both add production code, and a
  comparison introduced by either would make an allowlist authored earlier stale. Sequencing this plan
  last means the allowlist is authored once, against the code that ships.

- **P-27 — The receiver-name heuristic, as salvaged, and what the resource must say about it (CONTEXT.md
  Claude's Discretion on D-03).** A comparison token matches only when the identifier immediately to its
  left ends with `time`, `start` or `end`, or begins with `envelope`, `band`, `break` or `slot`,
  case-insensitively. Only the receiver is inspected, never the argument — inspecting the argument pulls in
  date and decimal comparisons this phase does not own. The resource must document the pattern list AND its
  three known limitations: it is name-based rather than type-aware, so a scheduling time held in a
  differently-named local escapes it and a date held in a matching-named local is caught spuriously; it
  inspects only the receiver, so a scheduling time appearing only as an argument escapes; and it tolerates
  exactly one trailing empty argument list, so a two-level accessor chain resolves to the nearest name
  rather than the true owner. A type-aware parser was evaluated and rejected as a new build dependency;
  revisit only if the heuristic proves noisy in practice.

- **P-28 — The synthetic offender's location and shape.** `src/test/resources/midnight-guard-offender/OffendingSample.java`.
  It must end in `.java` because the scan filters on that extension, and it must live under
  `src/test/resources` because resources are copied, never compiled — so a deliberately offending file
  cannot break the build and cannot poison the source tree if a run is killed. It contains exactly two
  interesting lines: one real offending comparison on a scheduling-time-named receiver, and one *commented*
  line naming the same token. The pipeline must therefore yield exactly one entry, which proves the
  comment-strip step as well as the walk and the match — a two-entry result means comment stripping
  silently stopped working.

- **P-29 — How the source root is parameterised.** Extract the walk into a method taking the root and the
  matcher, keep the production root as the existing constant, and have every real assertion pass that
  constant. The fully-qualified-name derivation must take the root too, since it relativises against it.
  The existing scan-sees-production-source check must keep asserting against the production root
  specifically — if the parameterisation accidentally leaves a real assertion pointed at the fixture
  directory, that assertion silently stops guarding production while still passing.

- **P-30 — If the allowlist does not match the settled tree, reconcile deliberately.** RESEARCH.md expects
  the salvaged ten-entry comparison allowlist to apply close to cleanly, because the one relevant fix that
  landed since the rescue tag was itself salvaged forward. If the scan finds a comparison the allowlist does
  not carry, it is either a genuine new offender introduced by this phase — route it through the day-window
  utility, do not allowlist it — or a pre-existing legitimate start-to-start comparison, which may be
  allowlisted only with a written justification meeting the resource's own both-endpoints-are-starts test.
  If the allowlist grows past roughly fifteen entries, the heuristic is too loose and is catching date or
  decimal comparisons: report that rather than absorbing it, because a ballooning allowlist is the
  guard-becomes-decoration failure the class's own javadoc warns against.
</planner_decisions>

## Trust Boundaries

This plan adds no production code. The boundary that matters is the build's trust in its own guard.

| Boundary | Description |
|----------|-------------|
| build → the guard's verdict | A green build is taken as evidence no scheduling-time comparison bypasses the shared utility |
| guard → its own fixture | The synthetic offender is the only thing standing between "the guard can fail" and "the guard has never been shown to fail" |
| test resources → compiled source sets | A deliberately offending `.java` file must never be compiled |
