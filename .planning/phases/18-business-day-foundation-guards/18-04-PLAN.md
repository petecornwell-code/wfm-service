<planner_decisions>
- **P-16 — The deterministic pinning rule (CONTEXT.md Claude's Discretion on D-14).** The model has
  exactly two planning variables: `AgentAssignment.agent` (nullable) and
  `AgentShiftAssignment.shiftBandPair` (allows unassigned). The rule is **index-modulo round-robin over
  a stably sorted candidate list**:
  - Sort every `AgentAssignment` by its timeslot's calendar date, then its timeslot's start
    minute-of-day, then its own id. Sort the eligible agents by id. Assign the i-th assignment the agent
    at index `i mod eligibleCount`, where "eligible" excludes any agent with no `AgentDayConfig` for
    that date or with non-positive effective hours — the same working-day gate the solver itself applies,
    which is what makes the pinned solution one the solver could actually reach.
  - Sort every `AgentShiftAssignment` by date then agent id, and assign the candidate at index
    `i mod candidateCount` from that entity's own value-range list.
  Every scenario must additionally argue, in a comment, why its pinned solution violates no hard
  constraint the scenario is not deliberately testing. Stated once here, restated in the fixture's
  javadoc, and never varied per scenario.

- **P-17 — One resource file for both the predicate list and the flip registry, two headings.**
  `src/test/resources/midnight-boundary-scenarios.md` carries `### Boundary predicates` (D-17) and
  `### Scenarios asserting today's behaviour` (D-16). CONTEXT.md leaves this to discretion subject to
  D-01's one-guard-one-resource rule: BDAY-06 is one guard, so it gets one resource, exactly as
  `midnight-time-arithmetic.md` carries two sections for one guard. Both sections are parsed by the same
  first-fenced-block-after-heading helper already proven three times in this codebase.

- **P-18 — The "cannot exist today" mark is a runtime annotation, not a comment or a JUnit tag.** A new
  `@AssertsTodaysBehaviour(flippedBy = "<requirement id>", to = "<the new expected behaviour>")` in
  `com.wfm.support`, retained at runtime, targeting methods. The validator reflects over both scenario
  classes' declared methods and asserts set equality against the parsed registry, rendering each entry
  as `<fully qualified class>#<method> -> <flippedBy>`. Reflection rather than a source grep, so the mark
  cannot be satisfied by a comment; including `flippedBy` in the rendered key means changing which
  requirement owns the flip also fails until the resource is updated.

- **P-19 — Assumption A1 is settled behaviourally, not by reading a javadoc.** RESEARCH.md flagged that
  `SolutionManager.update`/`.explain`'s pure-evaluation semantics were confirmed from general
  documentation rather than the pinned `timefold-solver-core:1.16.0` javadoc. The suite proves it at
  runtime instead: one scenario pins a deliberately sub-optimal assignment, records every planning
  variable, computes the score, and asserts every planning variable is unchanged. A search would have
  moved at least one. That assertion is a permanent guard, not a one-off check, and it is stronger than
  any javadoc read. Consult the pinned artifact's javadoc as well if it is convenient, but the test is
  the gate.

- **P-20 — Which scenarios are constraint-level and which are plain unit tests.** D-15 assigns three
  named scenarios to plain unit tests. Applying its rule — only genuinely constraint-level properties get
  a pinned-solution evaluation — across ROADMAP success criterion 4's six scenarios gives:

  | Scenario | Home | D-16 marked? |
  |---|---|---|
  | A 23:00-to-00:00 slot's interval arithmetic | plain unit | no |
  | An envelope flush to end-of-day, at save time | plain unit | no |
  | Contracted hours consumed by the starting weekday only | plain unit | **yes** — OVNT-04 flips it |
  | A shift starting before and ending after midnight | plain unit | **yes** — OVNT-01 flips it |
  | A break band flush to an envelope edge, scored | pinned evaluation | no |
  | PTO on the starting versus the ending calendar day | pinned evaluation | **yes** — OVNT-03 flips it |
  | A 23:00-to-00:00 timeslot's coverage scoring | pinned evaluation | no |

  The registry therefore spans both classes, which is why the validator resolves classes by name rather
  than living inside one of them.

- **P-21 — The fixture is new work, not an extension of an existing one.** `ShiftModeFixtures` builds a
  complete `Schedule` with deterministic ids and is the right idiom to follow for assembling problem
  facts by hand, but its envelope is 08:00 to 17:00 and other suites depend on its exact shape.
  Parameterising it to reach midnight would change fixtures those suites assert against. The new fixture
  borrows the assembly idiom and builds its own scenarios. Neither
  `ConstraintPrecedenceObservabilityTest` nor `ShiftEnvelopeGroundTruthTest` may be used as a base class:
  both reach their starting `Schedule` by calling `solve()`, which D-14 forbids.
