<task type="checkpoint:decision" gate="blocking">
  <decision>Which mechanism carries the desk's day start into `honourPreferredBreakTime`</decision>
  <context>
Eighteen of the nineteen interval-anchor call-site occurrences have an established mechanism. Five
constraints (`exactlyOneBreak`, `breakDuration`, `breakBlockedWindow`, `breakStartAlignment`) reach
four-member tuples with the agent-day configuration already among them, so they read the anchor off it at
zero extra join cost. `shiftWorkContiguity`'s stream is genuinely two-member before its mode gate and its
lead entity already carries a populated agent-day configuration, so it reads the anchor the same way.

`honourPreferredBreakTime` is the one genuinely open site, and research flagged it as the single novel
engineering problem in this phase's scope. Its stream reaches four members — agent id, date, the assignment
list, and the agent preference — and the agent-day configuration is NOT among them: this constraint joins
the preference instead. Timefold 1.16.0 has no five-member constraint stream, so the anchor cannot simply
be joined in, and the two sound mechanisms differ in ways worth a deliberate choice rather than an
executor's judgement call mid-commit.

Both options give up the same thing: today this constraint's grouping is deliberately keyed on the agent id
rather than the agent object specifically so it shares a grouping node with six sibling constraints — the
in-code comment says so. Either option ends that sharing, which is a scoring-performance cost on every
solve, not a correctness cost.

What makes this worth stopping for: both options can change this constraint's match COUNT, and two
assertions already committed in this phase pin that count — the per-constraint anchor-invariance assertion
and the 48-agent drift baseline. A count change would look exactly like the silent-non-join defect the
phase exists to catch, and the prohibition against editing a baseline to make a test pass means there is no
cheap way out at execution time.
  </context>
  <options>
    <option id="tagged-collector">
      <name>Join the schedule configuration before the grouping and fold the anchor into a tagged collector</name>
      <pros>Keeps the grouping keys exactly as they are — agent id and date — so the group identity, and therefore the match count, is unchanged by construction. Reuses the tagged-value technique already present in this file for break clustering, so it is a known shape in a known place. The smallest conceptual change: the constraint still reads "group an agent's day, then join the preference".</pros>
      <cons>Needs a custom collector returning a small record that carries both the assignment list and the day start, which is more machinery than any other site in this migration. The schedule-configuration join must move ahead of the grouping, which is where the node sharing is lost. More code in the riskiest commit of the phase.</cons>
    </option>
    <option id="lead-from-agent-day-config">
      <name>Lead the stream from the agent-day configuration instead of from a bare assignment grouping</name>
      <pros>Lands at three tuple members rather than four, with room to spare, and the day start is simply a field on the lead entity — no collector, no tagged record, materially less code. The agent-day configuration is the natural lead for a constraint that is about an agent's day. Leaves the file easier to read afterwards.</pros>
      <cons>Changes the group identity from the agent-id-and-date pair to the configuration object. For a working agent-day the two are one-to-one, so the count should be preserved — but it is a behavioural change at one edge: an agent-day that has assignments and NO configuration produces a group today and would produce none afterwards. That case is separately penalised by the agent-not-working-that-day constraint, so no violation is lost, but the match count of THIS constraint could move, and two committed baselines pin it.</cons>
    </option>
  </options>

If the chosen option turns out to move this constraint's match count once implemented, the executor must STOP and report the moved count rather than updating either baseline.</resume-signal>
