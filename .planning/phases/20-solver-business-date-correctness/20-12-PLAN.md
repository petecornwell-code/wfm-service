<objective>
Close `20-REVIEW.md` CR-01 and WR-01: the problem-fact and snapshot fetches that pass **business-date**
period bounds (`Schedule.periodStartDate`/`periodEndDate`, locked by `18-CONTEXT.md` D-22) into
**calendar-date** repository finders, silently dropping the last business day's post-midnight rows on
any re-anchored desk.

Purpose: plans 20-10 and 20-11 fixed `expandMinimumStaffingSeats` and `runPreSolveValidation` to read
`Timeslot.getBusinessDate()`. Both of those methods consume a list loaded **upstream** of them, at
`SolverService.java:180-185`, by two finders that filter the `date` (calendar) column. On a 21:00-anchored
desk with a one-business-day period, business-Monday's 24 timeslots split 3 rows on calendar Monday
(21:00-23:59) and 21 rows on calendar Tuesday (00:00-20:59); `DateBetween(businessMonday, businessMonday)`
admits only the first 3. The two fixed methods are therefore correct about data that has already been
truncated. The same truncation sits in `ScheduleService.acceptSchedule`, where it is **permanent** —
an incomplete timeslot and demand set is written into the ACCEPTED snapshot.

Output: one shared widen-then-derive loader, all four call sites re-pointed at it, the accept path proven
end-to-end against a real database at a 21:00 anchor with a midnight-anchored control, and the repository
finder-name shape recorded in `bday-join-guard.md` as the blind spot that let these four sites survive
plan 20-11's audit.

**The fix pattern already exists in this repository and is not being invented here.**
`TimeslotGeneratorService.generateTimeslots`' closing read-back (`:189-208`, BDAY-03) widens its calendar
upper bound by one day, then filters and orders on the **derived** business date — never the stored
`business_date` column. This plan mirrors that method. `20-REVIEW.md` CR-01's own suggested fix (new
`...AndBusinessDateBetween...` finders reading the stored column) is **rejected** by this plan's first
prohibition.
</objective>

<planner_decisions>
- **P-01: one shared static loader, not four inlined copies of the pattern.** New package-private final
  class `com.wfm.service.BusinessDayPeriodLoader` with a private constructor and two package-private
  statics. Four inlined copies is exactly the "two implementations that can disagree" failure this project
  rejects by standing rule (Phase 14 D-08: "The report an operator reads and the refusal that blocks them
  can never disagree"), and it is how this defect class has repeatedly survived — one site gets fixed, its
  siblings do not. A single named class is also a grep-able target the WR-01 documentation entry can name.
- **P-02: timeslots are re-sorted on the derived key; staffing requirements are filtered ONLY.** The
  timeslot finder carries `OrderByDateAscStartTimeAsc`, so re-sorting on
  `(businessDateOf(...), startMinuteFromDayStart(...))` preserves the order exactly at a 00:00 anchor
  (`businessDate == date`, and `startMinuteFromDayStart(MIDNIGHT, t)` is `t`'s minute-of-day) while making
  the business-day ordering explicit instead of incidental — which also discharges IN-01. The unpaginated
  `findLiveByDeskAndDateRange` JPQL carries **no** `ORDER BY`, so imposing one there would change the
  returned order at a 00:00 anchor and break the no-op invariant. Filter only; a stream filter preserves
  relative order.
- **P-03: the anchor is passed in, never re-derived.** `SolverService` passes `desk.getDayStart()` — the
  same already-loaded `Desk` that bound `window` at `:172`, so no second anchor source enters that class.
  `ScheduleService` passes `schedule.getDayStart()`, written by `SolverService.buildSchedule:655` onto the
  in-memory `Schedule` that `acceptSchedule` reads out of `InMemoryScheduleStore` — so the accept path and
  the solve path provably resolve the identical anchor, with no new `DeskRepository` lookup and no
  `DayWindow` anchor getter.
- **P-04: no midnight fallback in `ScheduleService`.** If an existing fixture crashes on a null `dayStart`,
  it is fixed at the test level with an explicit `setDayStart(LocalTime.MIDNIGHT)` — plan 19-05's recorded
  decision for exactly these files. `ScheduleServiceShiftSnapshotTest.buildInMemorySchedule` already does
  this at `:891`, so no pre-existing fixture is expected to break.
- **P-05: `startSolve` itself is not put under test; the proof is split.** `startSolve` takes twenty
  injected collaborators and launches a real solve, and `20-REVIEW.md` itself notes its recommended
  regression test would need a new harness. Instead the chain is proven in two halves, the same
  decomposition plan 20-11 used: **behaviourally** at the loader (`BusinessDayPeriodLoaderTest`, plus the
  real-database accept-path proof that exercises both loader methods end-to-end), and **structurally** at
  the call sites (comment-stripped greps proving no site bypasses the loader). Neither half alone is
  sufficient; together they cover load correctness and call-site coverage.
- **P-06: the tracer is the accept path, not the solve path.** `ScheduleServiceShiftSnapshotTest` is an
  existing `@DataJpaTest` harness with a real database, real repositories and a real `acceptSchedule` call.
  Routing the tracer through it gives a genuine end-to-end slice — service call site → widened repository
  query → `DayWindow` derivation → persisted snapshot rows — in one test, exercising both loader methods.
  No comparable harness exists for `startSolve`.
</planner_decisions>
