<objective>
Make the expanded weekday row editable: each weekday becomes a type-or-pick control covering all
five stored states, and the surviving seven-row fan-out becomes an explicitly labelled, warning-
guarded bulk action rather than the roster's default hours-edit path.

Purpose: D-05 closed audit finding I-3 structurally on the backend (one edit, one row). This plan
gives the operator the affordance that uses it, and completes D-07 by relabelling the fan-out and
warning before it overwrites any MANDATORY or PTO label — the failure the audit found and Phase 9
D-10 requires be preserved rather than removed.

Output: a `setDayHours` API-client call, a per-cell combo built on a native `datalist` with zero new
dependencies, and a relabelled bulk action with the project's existing amber warning treatment and
native confirmation.
</objective>

<planner_decisions>
- **P-10 — client-side validation checks the range, not the quarter-hour step.** A typed value is
  accepted when it parses as a number in the inclusive range 0 to 24; it is rounded to two decimal
  places for display and sent as typed. It is NOT rejected for failing to be a multiple of 0.25.
  Rationale: the backend accepts any two-decimal value in range, and the upload parser can already
  have stored one — rejecting non-quarter values client-side would make an uploaded `7.60` literally
  uneditable through the UI, which contradicts the point of the phase. D-03's "quarter-hour steps"
  is honoured as the bulk input's `step` affordance, which is a hint rather than a gate.
  Reversibility: reversible.

- **P-11 — no frontend test framework is introduced (adopts 13-RESEARCH.md Wave 0 Gaps option b).**
  This project has zero `vitest` / `jest` / `@testing-library` anywhere; installing one would be a
  new-dependency decision requiring its own package-legitimacy pass and would exceed this phase's
  stated blast radius. The frontend surface is verified by `tsc -b` plus the `<human-check>` blocks
  below, which the verifier harvests into the phase UAT. Reversibility: reversible.
</planner_decisions>

| T-13-14 | Tampering | client-side range validation on the combo | medium | mitigate | Client validation is a UX affordance only; the authoritative 0-to-24 range check, HALF_UP normalization and enum binding all run server-side in plan 13-02 and are covered by `setDayHours_above24_isRejectedAndPersistsNothing` and `setDayHours_negative_isRejectedAndPersistsNothing`. No behaviour depends on the browser having validated first |
| T-13-15 | Tampering | operator-typed text reaching a rendered cell | low | mitigate | Typed text is either resolved to a number, to one of two enum keywords, or to a clear-row flag before any request; unrecognised input is rejected client-side and never stored. | T-13-17 | Denial of Service | rapid repeated cell edits | low | accept | Each edit is a single small row write already guarded by the in-flight disable; no rate limiting exists anywhere in this application today and adding it is out of this phase's scope |
