<planner_decisions>
- **P-20 — bands are a plain `useState` array, no library.** `DeskAgents.tsx`'s `.map()` usages are
  all over fixed or pre-populated collections; there is no existing "append a blank row to a growing
  form array" precedent anywhere in this codebase. Implement it as `useState<BandRow[]>` with
  spread-append and index-filter removal, following the codebase's hooks-only, zero-UI-dependency
  convention. This is a new interaction pattern with no sibling to imitate, and it stays deliberately
  primitive for that reason.
- **P-21 — the offset conversion is per band.** Phase 14 converted one wall-clock break start into
  `breakOffsetMinutes` client-side immediately before the request. That conversion runs once per band
  now, using the same `toMinutes` helper already in the file. The editor's control type stays
  `<input type="time">` for band start, unchanged.
- **P-22 — `CoveragePanel` is reused verbatim for partial coverage.** The UI-SPEC's instruction is
  explicit: do not build a second uncovered-windows renderer. The generation response emits the same
  `ErrorDetail` shape SHLB-05 already emits, so the existing component takes it unmodified.
- **P-23 — the capacity advisory reuses SHLB-06's glyph-plus-tooltip mechanism**, placed as a new
  column adjacent to the existing "Hours match" column, warning-amber, non-blocking. No new visual
  pattern is invented; the mechanics are locked by the UI-SPEC even though the column naming was left
  to the planner. Name the column `Capacity`.
- **P-24 — draft rows are always-editable, saved templates are not.** A deliberate, named exception
  to the list's view-then-click-Edit pattern: the whole point of a draft is fast pre-save iteration,
  not a second read/edit mode distinction.
</planner_decisions>

In `client.ts`, replace the four scalar break fields on `ShiftTemplate` and the two on
`ShiftTemplateBody` with a `bands` array. Declare `ShiftTemplateBreakBand` as
`{ id: string; offsetMinutes: number; durationMinutes: number; breakStartTime: string;
breakEndTime: string; capacity: number | null; netHours: number }` for the response side and
`ShiftTemplateBreakBandBody` as `{ offsetMinutes: number; durationMinutes: number;

`ShiftLibraryValidation` type as an array of
`{ templateId: string; templateName: string; weekday: string; capacityTotal: number;
admissibleHeadcount: number; message: string }`, following `hoursAdvisories`' existing shape.

In `ShiftLibrary.tsx`, change `TemplateFormState`'s `breakStartTime`/`breakDurationMinutes` scalars
into `bands: BandRow[]` where `BandRow` is `{ breakStartTime: string; breakDurationMinutes: string;
capacity: string }` — strings throughout, matching how every other numeric input in this form is held
(P-20). `emptyForm()` returns an empty band array, so a fresh Add form starts with no bands, which is
the valid "no break" state rather than a seeded blank row.

Replace the form's "Break start time" and "Break duration (minutes)" field pair with the band editor
of UI-SPEC § Component Specifications 1: a `Break Bands` sub-label at the Label role (13px/600) above
a vertical list of band rows with an 8px gap, inside a 12px-padded box matching the form's existing
field-group chrome. Each band row carries a band start `<input type="time">`, a duration
`<input type="number" min="0">`, a capacity `<input type="number" min="1">` with placeholder
`Unlimited` and **no** default value, and a small plain `Remove` button at the row's end sized like
the existing edit-mode Save/Cancel controls. Beneath each row render the per-band preview line in the
muted grey already used for Phase 14's single preview:
`Break {bandStart}–{bandEnd} ({duration}m) · {capacityText}, net {X}h worked.` where `capacityText`
is `capacity {N}` when set and `unlimited` when blank — always rendered explicitly, never omitted, so
blank reads as a deliberate choice. Beneath the list, a plain-weight `+ Add Break Band` button
appending `{ breakStartTime: '', breakDurationMinutes: '0', capacity: '' }`. When the band list is
empty, render the muted line `No break bands added — this template has no break.` in place of the
list, with `+ Add Break Band` still available beneath it; this is a valid state and gets no
amber/warning chrome. Both new buttons are deliberately plain, not accent — the page's one accent
element stays `Add Shift Template`, and `+ Add Break Band` is a nested sub-action inside a form that
already has its own accent `Save`.

Extend `formToBody` to map each band row through the existing `toMinutes` helper — offset is the
band start minus the template start (P-21) — emitting `capacity: null` when the capacity input is
blank and a parsed integer otherwise. Extend `startEdit` to seed one band row per existing band from
the template's current values, offset-ascending, mirroring the existing seeding pattern extended from
a scalar to a list.

Route per-band grid-misalignment errors to the offending row: the backend emits one `ErrorDetail`
per offending band whose `field` identifies the band by index, so key `fieldErrors` by that
band-scoped field name and render the inline amber error beneath that band's own row rather than once
for the whole form. Keep the existing inline-error placement and colour; do not use a toast for this.

Reuse Phase 14's existing `submitting` flag for the band-row inputs — the form-level loading state is
unchanged and now also disables band controls.

Add a plain-weight `Suggest a Library` button beside the existing accent `Add Shift Template` in the
page's top toolbar row. It is deliberately not accent-coloured: a suggestion is an assist, not a more
important way to build a library, and a page with three accent-blue buttons stops the colour meaning
anything. While in flight it reads `Suggesting...` and disables, matching the page's existing
boolean-flag convention (`switchingMode`, `submitting`).

Render the Suggested Library section between the template list and the Coverage panel, per UI-SPEC
§ Component Specifications 3. Before the operator has ever clicked, the section renders **nothing at
all** — no heading, no panel, no persistent empty slot. On first request it appears with the heading
`Suggested Library` at the Heading role (18px/600) and, whenever a draft is present, a `Draft` badge
beside it in the existing neutral-grey badge token.

Handle the three possible results of the one call:

Refused — the request returns a 400 whose `details` carry the generation refusal. Render the section
heading with **no** `Draft` badge (nothing was generated) followed by the amber refusal panel
carrying the message the server sent, styled identically to the existing zero-demand Coverage-panel
state. Never an empty draft table.

Full coverage — render the draft rows with no additional coverage block. The presence of complete
rows already implies success; no new confirmation sentence is added.

Partial coverage — render the draft rows plus the existing `CoveragePanel` component reused verbatim
beneath them, fed the response's own `uncoveredWindows` list (P-22). Do not build a second
uncovered-windows renderer; the panel an operator reads after generating must be the panel they read
after validating.

Draft rows are always-editable (P-24), reusing the same field set and controls as the Add/Edit form —
name, start and end time, the band editor from Task 1, weekday checkboxes, effective from/to. Per row:
an accent `Save` that commits that one row through the existing create call, on success removing it
from the draft and letting it appear in the saved template list exactly as a manual add would; and a
plain `Drop` that removes the row from the in-memory draft with no request sent. A saved row's own
grid or hours errors surface through the identical inline and toast mechanisms a manual create uses —
no draft-specific error path.

Wrap the draft rows in a container with a **dashed** border in the existing grey border token — a
structural treatment, not a new colour — and put the line
`This draft isn't saved — edits are lost if you navigate away.` at the top of the panel whenever a
draft is present, making the endpoint's statelessness an operator-visible fact rather than a silent
trap. Default field values for a freshly generated row come from the server: name `Suggested {n}`,
effective from today, effective to blank.

Clicking `Suggest a Library` again while a draft is present replaces the entire draft in place and
discards any unsaved edits to the previous one, with no confirmation dialog — nothing generated has
ever been persisted, and the discard-notice line already sets that expectation. This is the same
no-dialog-on-a-non-destructive-action rule Phase 14's D-12 established, citing audit I-3: a dialog on
a harmless action trains operators to click through the ones that matter. This phase introduces no
destructive action and no `#ef4444` element.

| server response → rendered text | Advisory, error-detail and uncovered-window strings are rendered into the page; they originate server-side and are scoped to the caller's own tenant |
| draft row → create endpoint | A draft row is client-held, freely edited data; on save it is untrusted input to the server's create/validate path |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-15-18 | Information Disclosure | advisory and error text rendered in the page | medium | mitigate | Every string comes from `ShiftLibraryValidationService` or `ShiftLibraryGenerationService`, both of which resolve `TenantContext.getTenantId()` at the top of every public method and never accept a caller-supplied tenant, so a message can only name the requesting tenant's own templates, weekdays and demand windows. |
