<objective>
Prove the shift-mode solve is feasible and that its reported score agrees with an independent check
of the resulting schedule — walked outside the score director, on a code path that shares nothing
with the constraint it is checking.

Purpose: `SPIKE-COUPLING.md`'s central finding is that a structurally unsound coupling computes an
internally consistent but wrong score. Option C compiled, ran clean under `FULL_ASSERT`, and reported
`0hard/0soft` on 8/8 seeds while 9–14 of 24 seats sat outside their agent's envelope. No Timefold
assertion mode can catch that, because `FULL_ASSERT` only checks score consistency, never
value-range validity. The only thing that catches it is an external walker.

Output: a reusable shift-mode fixture builder and the ground-truth test — the check that would have
caught Option C.
</objective>

<flagged_assumptions>
The deterministic edge probe left **ENVL-06** unclassified. Surfaced here as an explicit planner
assumption rather than dropped or auto-resolved:

- **ENVL-06 (unclassified by the probe).** The requirement — "the solver reaches a feasible initial
  solution on a shift-scheduled desk without any pre-assignment pipeline" — is a *process* claim
  about the construction heuristic, not a data shape, so no edge category applies. The planner's
  assumption: "feasible initial solution" means the construction heuristic alone (before any local
  search step) leaves every `AgentShiftAssignment` and every `AgentAssignment` placed by the solver
  rather than by application code, and the resulting solution's hard score is reachable to zero
  within the fixture's step budget. Task 1 asserts both halves explicitly rather than inferring
  feasibility from a terminal score. If a fixture cannot reach `0hard` within budget, that is a
  finding for plan 15-08's benchmark to quantify, not a licence to relax this assertion.
</flagged_assumptions>

<planner_decisions>
- **P-17 — the walker shares no code with the constraint.** `ShiftEnvelopeGroundTruthTest` computes
  envelope membership from raw `LocalTime` comparisons written in the test file itself. It must not
  call `ShiftBandPair.covers`, must not call `ScheduleConstraintProvider`, and must not go through
  `SolutionManager` or any score director. A walker that reuses the production predicate inherits the
  production bug and proves nothing — that is precisely how Option C passed everything that was
  pointed at it.
- **P-18 — solve through the real `SolverFactory`, not a hand-built `SolverConfig`.** The point is
  to exercise the shipped `solverConfig.xml`, including its two construction-heuristic phases.
  Terminate by step count, never wall-clock, so the test is reproducible in CI.
- **P-19 — the fixture builder is extracted, not inlined.** `ShiftModeFixtures` is created here and
  reused by plan 15-06's mode-gating and clustering fixtures and plan 15-08's benchmark, so the three
  agree on what a shift-mode `Schedule` looks like. Building it three times would be three chances to
  build a subtly different one.
</planner_decisions>

Create `ShiftModeFixtures` as a package-visible test helper building a complete shift-mode
`Schedule` in memory: a desk in SHIFT mode, a timeslot grid over an operating window with a stated
increment, staffing requirements producing demand on every slot, a small agent roster all contracted
to the same hours, `AgentDayConfig` rows for each agent-day, a shift library of two or three banded
templates whose net durations match those contracted hours exactly, the derived sorted
`List<ShiftBandPair>`, one `AgentShiftAssignment` per working agent-day with its day config and the
pair list attached, expanded `AgentAssignment` seats, `ConstraintWeights` with the shipped defaults,
and a `ScheduleConfig` carrying SHIFT mode. Expose parameters for agent count, day count, template
set and band count so plans 15-06 and 15-08 can vary them, and a sibling builder producing the same
fixture in SLOT mode with zero shift rows and zero pairs. Keep the builder deterministic — no random
ids that vary per run beyond what the test seeds explicitly.

Create `ShiftEnvelopeGroundTruthTest`. Build the fixture, obtain a solver from
`SolverFactory.createFromXmlResource("solverConfig.xml")`, configure a step-count termination
(never wall-clock — P-18), and solve.

Assert feasibility first, and assert it non-vacuously: the solved schedule's
`shiftAssignments` list is non-empty, every one of them holds a non-null `shiftBandPair`, the
`assignments` list is non-empty, and the count of seats with a non-null agent is greater than zero.
A walker that finds zero violations across zero seats is a vacuous pass, and vacuous passes are the
failure mode ENVL-07 exists to close — this assertion is the plan's recorded prohibition made
mechanical. Then assert the reported hard score is zero.

Write the walker as a private static method in this test file, computing envelope membership from
raw values only (P-17): build a map from `(agentId, date)` to the row's chosen pair by iterating
`solved.getShiftAssignments()`; then iterate `solved.getAssignments()`, skip seats with a null agent,
look up the pair, and record a violation string when the pair is null, or when the seat's timeslot
start is before the template's start time, or the seat's timeslot end is after the template's end
time, or the seat's timeslot overlaps the band's break interval computed as the template start plus
the band offset through plus the band duration. Compare `LocalTime` values directly with `isBefore`
and `isAfter`; do not round, and do not call `ShiftBandPair.covers` or any production helper. Assert
the returned violation list is empty, and on failure report the offending agent, date, timeslot and
template so a red run is diagnosable without a debugger.

Add an assertion that the two answers agree in the affirmative direction as well as the negative:
the walker's violation count is zero **and** the score's hard component is zero, asserted as one
compound claim, so a future change that makes one true while the other is false fails here rather
than silently at UAT.

<task type="auto">
  <name>Task 2: The disagreement proof — the walker must be able to fail, and specialization must stay free</name>
  <files>src/test/java/com/wfm/solver/ShiftEnvelopeGroundTruthTest.java</files>
  <action>
A check that has never gone red proves nothing about its ability to go red. Add the negative cases,
constructing the violation by direct mutation of the solved solution rather than by trying to
persuade the solver to produce a bad one.

Case one — the leading edge. Take the solved fixture, pick one seated agent-day, and reassign one of
its seats to the timeslot exactly one increment before its template's start time. Assert the walker
now reports exactly one violation naming that agent, date and timeslot. This is the ENVL-07 boundary
truth: the walker must flag a seat exactly one timeslot outside the envelope, not only a grossly
outside one.

Case two — the trailing edge. The same construction at the other end: a seat in the timeslot starting
exactly at the template's end time. Assert exactly one violation. Assert additionally that a seat in
the timeslot *ending* exactly at the template's end time draws none, so the half-open boundary is
pinned in both directions.

Case three — inside the break. Move a seat into the timeslot starting exactly at the assigned band's
break start; assert one violation. Move it to the timeslot starting exactly at the band's break end;
assert none.

Case four — the null shift. Set one `AgentShiftAssignment`'s pair to null on the solved solution and
assert the walker reports a violation for **every** seat that agent holds that day, not just one —
the same behaviour plan 15-03's constraint test asserts from the score side, checked here from the
independent side.

Case five — score agreement on a broken solution. For case one's corrupted solution, obtain a fresh
score for the mutated solution through the solver's score director and assert its hard component is
non-zero. The requirement is that the two agree, which means agreeing that a broken schedule is
broken, not only agreeing that a good one is good. This is the assertion pair Option C would have
failed.

Case six — ENVL-03, specialization stays free. On the clean solved fixture, confirm that at least one
agent holds seats requiring two different specializations within the same shift, and assert the
walker reports no violation for it. If the fixture as built cannot produce that situation, extend
`ShiftModeFixtures` so its staffing requirements demand two specializations across the operating
window — the guarantee is worth a fixture change, and asserting it vacuously would be worse than not
asserting it.
