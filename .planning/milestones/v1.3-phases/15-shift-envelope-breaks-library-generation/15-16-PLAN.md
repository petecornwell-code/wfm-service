<objective>
Stop the read path from telling the operator things that are not true.

Two defects, found the same way — both cost a UAT session hours by misreporting reality, and neither
touches the solver or any stored schedule.

G-15-32: every accepted schedule on the live desk reports `Shift envelope compliance` with
`violationCount 1104` — a CONSTANT equal to 138 agent-days x 8 contracted hours, i.e. every staffed
seat. It is reported identically on schedules whose true violation counts are 12, 9, 1, 0, 0 and 0,
so it carries no information about the schedule it describes. `ScheduleService:159` derives
`violatedHardConstraints` from it, so a response reads `feasible: true` AND names a violated hard
constraint in the same body — telling an operator the phase's headline guarantee is broken on a
schedule where the server's own `divergence` field proves it holds.

G-15-26: `HttpRequestMethodNotSupportedException` has no handler, so the catch-all at
`GlobalExceptionHandler:105` turns a plain wrong-verb client mistake into 500 INTERNAL_ERROR. That
one 500 was read as a wedged desk, triggered an unnecessary ECS force-new-deployment and a failed
deploy re-run, and produced a BLOCKER gap entry that had to be fully retracted.

Purpose: make the API's violation report and its error report both describe reality, and add the
cheap read-path invariant whose absence let the first defect ship.

Output: an accepted-schedule violation report derived from the persisted snapshot, a
`feasible`/`violatedHardConstraints` contradiction that is structurally unreachable, a red-proof
that the new path can still go non-empty, and a 405 handler.
</objective>

On the accepted/DB path, never call `solutionManager.explain`. Explaining a schedule whose shift
problem facts are not reconstituted makes every held seat fail the coverage predicate — the file's
own DISCRIMINATOR IDENTITY for a null band pair — which is where the constant 1104 comes from.

rather than writing a second one:

- Walk the schedule's agent-days exactly as `buildAgentSchedule` does, resolving each agent-day's
  `ShiftDescriptor` through the EXISTING `resolveShiftDescriptor` (which already prefers a live
  transient pair and otherwise reads D-07's denormalised scalar columns).
- For each agent-day with a descriptor, obtain the out-of-envelope seats by calling the SAME
  `computeDivergence` the agent-schedule view already calls. Do not re-derive coverage arithmetic
  and do not add a third definition of "covered" — factor a shared private helper if the walk needs
  restructuring, but the predicate itself stays `ShiftBandPair.covers`.
- Aggregate every out-of-envelope seat across all agent-days into ONE `ConstraintViolationEntry`
  whose `constraintName` is character-identical to the name the score director uses for envelope
  compliance (take the constant from `ScheduleConstraintProvider` rather than retyping the string —
  the UI keys on this value and a divergence here would be silent), `level` HARD, `violationCount`
  the seat count, `weight` the schedule's own `ConstraintWeights` envelope-compliance weight, and
  `totalPenalty` that weight multiplied by the count. Emit one `ViolationDetail` per seat carrying
  the agent id, agent name, timeslot id and the same timeslot label format the live path builds.
- Emit NO entry when the count is zero, matching the live path's existing "skip a zero total"
  behaviour. A clean accepted schedule therefore returns an empty list, and that is now empty
  because it was computed, not because the path was disabled.

Record plainly in the method javadoc what this report does and does not cover on the accepted path:
the persisted snapshot carries the envelope and band scalars, so envelope compliance is derivable
and is derived; other constraints' problem facts are not reconstituted at accept time, so nothing
is reported for them. Reporting nothing for a constraint whose ground truth is absent is the honest
outcome; reporting it from a mis-explained score director is what produced this gap. Note in the
same javadoc that shift-work contiguity is ALSO derivable from the same snapshot (worked slots plus
the descriptor's break window) but is deliberately not derived here, because its structural walker
currently exists only in test source (`SolverQualityGuardTest.findSplitShifts`) and promoting it to
main source needs its own guard — so that it is a named, routable limitation rather than a silent
omission.

Then fix the propagation at `ScheduleService`'s `violatedHardConstraints` derivation. The derivation
itself stays as-is — it reads HARD entries out of `constraintViolations`, which is correct once
`constraintViolations` is correct. Add a comment at that site naming the invariant it now upholds
and pointing at G-15-32, so a future reader understands why the list is derived rather than stored.

DO NOT, under any circumstances, satisfy the invariant by emptying or filtering
`violatedHardConstraints` when `feasible` is true. That would hide a genuinely infeasible schedule —
the precise inverse of the defect being fixed. The invariant is asserted by Task 2's test; it is
never enforced by suppression.
