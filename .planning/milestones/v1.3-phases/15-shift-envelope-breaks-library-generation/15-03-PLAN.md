<objective>
The solver gains a second planning entity: on a shift-scheduled desk each working agent-day chooses
exactly one `(template, band)` pair from the desk's library, and a hard constraint forbids seating
that agent outside the chosen envelope.

Purpose: this is the phase's structural core and the first `solverConfig.xml` change of the
milestone. The coupling mechanism is settled — Option A, two independent `@PlanningEntity` classes
joined by a `ConstraintStream` hard constraint. `SPIKE-COUPLING.md` proved Option C (a filtered value
range reading another entity's genuine planning variable) empirically unsound: it compiled, ran
clean under `FULL_ASSERT`, and reported `0hard/0soft` while 9–14 of 24 seats sat outside their
agent's envelope, on 8/8 seeds.

Output: `AgentShiftAssignment`, `ShiftBandPair`, the two explicitly-scoped construction-heuristic
phases, `shiftEnvelopeCompliance`, and — landing in the same slice as the config change, not after
it — the test that actually builds a solver.
</objective>

<flagged_assumptions>
The deterministic edge probe left **ENVL-02** unclassified. It is surfaced here as an explicit
planner assumption rather than silently dropped or auto-resolved:

- **ENVL-02 (unclassified by the probe).** The requirement — "an agent is never assigned a seat in a
  timeslot outside their assigned shift envelope, enforced as a hard constraint" — has no edge
  category the engine could apply, because its content is a *coupling* claim rather than a data
  shape. The planner's assumption, stated for the record: the plain positive-join form
  (`forEach(AgentAssignment)` joined to `AgentShiftAssignment` on agent id and date, penalising a
  definite disagreement between two initialised variables) is sufficient, and a `null` chosen shift
  naturally forbids every seat because a null pair cannot cover any timeslot. RESEARCH.md § Open
  Questions item 2 flags this exact trace as needing verification rather than assumption — Task 3
  therefore asserts it with a unit test instead of reasoning about it. If the trace turns out
  otherwise, the fix is an explicit null branch in the same constraint, not a second constraint
  (D-06 rejects a dedicated "unassigned shift" penalty because it double-counts what
  `contractedHoursUnder`/`UnderZero` already penalise).
</flagged_assumptions>

<planner_decisions>
- **P-12 — one planning variable, `(template, band)`-valued.** `AgentShiftAssignment` carries a
  single `@PlanningVariable` whose value is a `ShiftBandPair` problem fact (D-04). A second
  `breakBand` variable whose range derived from the chosen shift would be a value range reading a
  genuine planning variable — Anti-Pattern 2 in `research/ARCHITECTURE.md`, the identical mechanism
  that made Option C silently unsound. A third planning entity would need a third explicitly-scoped
  CH phase when the CH XML nesting was the phase's one MEDIUM-confidence research item.
- **P-13 — entity-level `@ValueRangeProvider` filtered by a problem fact.** The provider lives on
  `AgentShiftAssignment` and filters the desk's live pairs by this row's `AgentDayConfig`
  `effectiveHours`. This is the sound use ARCHITECTURE.md § C sanctions — the dependency is on a
  problem fact resolved once per solve, never on another entity's genuine planning variable. Without
  the filter, `shiftEnvelopeCompliance` and the existing `contractedHoursOver`/`Under` constraints
  become jointly unsatisfiable for that agent-day and no amount of solver time fixes it.
- **P-14 — `allowsUnassigned()`, not `nullable = true`.** `AgentAssignment` still uses the form
  deprecated `forRemoval` since Timefold 1.8.0; the new entity uses the current form (D-06). This is
  a documented inconsistency between the two entities, accepted because retrofitting
  `AgentAssignment` is out of scope.
- **P-15 — shifts-first CH ordering is committed first, and is not the shipped decision.** D-08
  makes the ordering a measured question: plan 15-08's benchmark carries a third arm swapping the two
  `<constructionHeuristic>` blocks, and the winner ships. Nothing else in the XML changes between the
  arms.
- **P-16 — `shiftEnvelopeCompliance` uses `penalizeConfigurable` against a new weight column**, not a
  literal `HardSoftScore.ONE_HARD`. Every constraint in this provider is weight-driven and every
  weight is a per-desk configuration row rather than a code decision — the precedent `minimumStaffing`'s
  javadoc records explicitly. A hardcoded score would be the only constraint in the file an operator
  could not tune.
</planner_decisions>
