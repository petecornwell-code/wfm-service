# Phase 17 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Surfaces in scope (exactly two files — see `17-CONTEXT.md` D-11…D-14, D-04, D-10):**

1. `frontend/src/pages/ScheduleResults.tsx` — a new **Drift Report** tab (tab bar ~line 259;
   `PreferenceTab` at ~line 989 is the structural analog and template to follow), holding two
   sections: the per-agent-date drift table (DRFT-01…03) and the shift-template over-subscription
   ranking (DRFT-04).
2. `frontend/src/pages/ConstraintWeightsPage.tsx` — the `CONSTRAINTS` array (~line 6) gains two new
   ordinary weight rows and one non-score tolerance-band row (CONS-02, CONS-03, D-04, D-08, D-10).

**Also specified (document surface, no independent visual contract):**

3. `src/main/java/com/wfm/service/ScheduleExportService.java` — one new Excel sheet, mirroring
   `writePreferenceReport` (~line 172), with headers byte-identical to surface 1's table headers (D-14).

**Out of scope:** the Shift Library page (Phase 14/15 own it — DRFT-04's ranking is deliberately
*not* placed there, per D-13), the roster page (Phase 16 owns the usual-shift tile and editor,
untouched here), any mitigation UI for the over-subscription tension DRFT-04 surfaces (Backlog
999.4), and any change to slot-scheduled rendering anywhere.

**Nature of this phase:** two additive surfaces on two existing pages, not a redesign. Every token,
color, spacing value and copy convention below is inherited from `14-UI-SPEC.md`/`15-UI-SPEC.md`/
`16-UI-SPEC.md` unless a row explicitly says "new this phase." No component library, CSS framework,
or frontend test framework is introduced — standing project decision since Phase 13, reconfirmed
this session (`frontend/package.json` still has zero UI-library dependencies).

**Density constraint, stated explicitly so it is not silently re-opened:** the roster's 90px-tile
constraint (Phase 13's G-13-8, Phase 16's density note) does **not** apply here — neither new
surface lives inside that grid. `ScheduleResults.tsx`'s existing tabs already render full-width,
horizontally-scrollable tables (`overflowX: 'auto'` on the tab content container, ~line 261), and
`ConstraintWeightsPage.tsx`'s table has no fixed-width columns beyond the existing 70px score
inputs. Nothing in this phase assumes or requires generous horizontal space beyond what these two
pages already have — but nothing here should be read as *needing* the roster's compactness either.

**This phase adds no new color, no new typography size/weight, and no new spacing token.** Every
visual decision below is a reuse of an existing token, chosen specifically to satisfy the CONTEXT
instruction to "align with [Phase 16's roster tile], rather than inventing a second visual language
for the same concept" — extended here to the whole phase, not just the one distinction it was
written about.

## Component Specifications

### Focal points (one per surface)

| Surface | Primary visual anchor | Why |
|---|---|---|
| Drift Report tab, main table | The **Status column** | It is the entire reason DRFT-02 exists — an operator scanning the table must register `NO_USUAL_SHIFT`/`HONOURED`/`DRIFTED` before reading any other cell, so it gets the phase's only color-and-weight differentiation |
| Drift Report tab, popularity section | The **ranked row order itself**, not any single cell | DRFT-04's whole point is "which templates are most over-subscribed" — the list is pre-sorted descending, so position on the page *is* the signal; no rank number or bar chart is added |
| `ConstraintWeightsPage`, new rows | The **tolerance-band row's merged input**, and the **precedence note directly beneath the three new rows** | The band is the only non-score field on the page — Component Specifications §3 exists entirely to make it read as a deliberate different-kind-of-field rather than a malformed score row; the precedence note is what makes CONS-06 "observable" rather than left for a reader to infer from row order alone |

### 1. Drift Report tab — main table (DRFT-01, DRFT-02, DRFT-03, D-11, D-12)

**Where:** `frontend/src/pages/ScheduleResults.tsx`. Add `'drift'` to the `activeTab` union type
(~line 16), add a tab button between `'preferences'` and `'violations'` in both the array literal
(~line 254) and the label ternary (~line 258), and render `<DriftTab schedule={schedule}
dateFilter={dateFilter} />` alongside the other tab-content branches (~line 269), following
`PreferenceTab`'s exact call shape (`schedule`, `dateFilter` props only — no new page-level state).

**Data contract this component needs (flag for planner/executor):** mirroring `PreferenceReport`'s
shape exactly (`ScheduleDetail.preferenceReport`, `frontend/src/api/client.ts:453`):

```ts
interface DriftReportEntry {
  agentId: string
  agentName: string
  date: string
  status: 'NO_USUAL_SHIFT' | 'HONOURED' | 'DRIFTED'
  usualStartTime: string | null   // null only when status === 'NO_USUAL_SHIFT'
  actualStartTime: string         // the assigned shift envelope start (D-03) — always present for a working agent-day
  deltaMinutes: number | null     // populated ONLY when status === 'DRIFTED' (D-12, literal)
}
interface DriftSummary {
  workingAgentDays: number
  noUsualShiftCount: number
  honouredCount: number
  driftedCount: number
}
interface ShiftPopularityEntry {
  templateName: string
  agentCount: number
}
interface DriftReport {
  entries: DriftReportEntry[]
  summary: DriftSummary
  popularity: ShiftPopularityEntry[]   // pre-sorted descending by agentCount, alphabetical tie-break
}
```
The component branches on `status` only — it never independently re-derives whether a deviation is
within the tolerance band (the same "one calculation, two callers" discipline DRFT-03 requires of
the backend, mirrored here as "the frontend renders, it does not recompute").

**Top-level branch (mirrors `AgentAllocationTab`'s `schedulingMode !== 'SHIFT'` branch-at-the-top
discipline, `15-UI-SPEC.md` §4 — locked design decision, not left to the planner):**

```
if (schedule.schedulingMode !== 'SHIFT') → render only the slot-scheduled empty message
else → render Summary bar, D-11 note, main table, then Section 2 (popularity)
```

**Why the whole tab — including Section 2 — is gated on `schedulingMode`, not just the main
table:** D-13 places the popularity ranking "next to the drift it explains" specifically so the
consistency-versus-fairness tension sits beside its cause. On a slot-scheduled desk there is no
drift to explain (no `AgentShiftAssignment` concept exists), so showing subscription counts alone,
without that context, would contradict D-13's own placement rationale. One `not applicable` message
covers both sections, exactly as `AgentAllocationTab`'s single branch covers its whole grouped view.

**Summary bar (new, mirrors `PreferenceTab`'s exact style,** `frontend/src/pages/ScheduleResults.tsx:1000`,
`display: flex, gap: '1.5rem', marginBottom: '1rem', fontSize: '0.85rem', background: '#f9fafb',
padding: '0.75rem', borderRadius: '6px'`): four `Label: **value**` pairs (Copywriting Contract),
computed from `report.summary` — counts reflect the **currently date-filtered** entry set (same
scope as the table beneath it), not the whole schedule, so the numbers always agree with what the
operator can see on screen.

**D-11 note, directly beneath the summary bar:** `fontSize: '0.75rem', color: '#6b7280',
fontStyle: 'italic', marginBottom: '0.75rem'` — the exact copy above, always rendered (not
conditional on any state), since the consequence is true of every drift report, not a specific one.

**Table (mirrors `PreferenceTab`'s exact table shell):** `width: '100%', borderCollapse: 'collapse',
fontSize: '0.85rem'`; header cells `textAlign: 'left', padding: '6px 8px'` (right-align `Delta
(min)` only, matching `StaffingTab`'s right-aligned `Delta` column); body cells `padding: '4px 8px'`.

**Row rendering, exact per status:**

| Status | Status cell | Usual Start | Actual Start | Delta (min) |
|---|---|---|---|---|
| `NO_USUAL_SHIFT` | `No usual shift`, color `#6b7280`, weight 400 | `—` | `{actualStartTime}` | `—` |
| `HONOURED` | `Honoured`, color `#15803d`, weight 400 | `{usualStartTime}` | `{actualStartTime}` | `—` |
| `DRIFTED` | `Drifted`, color `#dc2626`, weight 600 | `{usualStartTime}` | `{actualStartTime}` | `{deltaMinutes > 0 ? '+' : ''}{deltaMinutes} min`, right-aligned, same color `#dc2626` |

Delta sign convention matches `StaffingTab`'s exact existing pattern (`ScheduleResults.tsx:864`,
`{value > 0 ? '+' : ''}{value}`) — a negative number's own `-` renders unprefixed; positive gets an
explicit `+`. Positive means later than usual, negative means earlier — no separate "early/late"
word is added, the sign carries it.

**Filtering:** respects the page-level `dateFilter` exactly as `PreferenceTab` does (`dateFilter ?
entries.filter(e => e.date === dateFilter) : entries`) — no independent per-tab filter control is
added.

**Sort order:** entries render in the order the backend returns them. Data-contract expectation for
the planner: date ascending, then agent name ascending — no client-side re-sort, matching every
sibling report tab's convention of trusting server order.

### 2. Drift Report tab — Usual Shift Popularity section (DRFT-04, D-13)

**Where:** same file, same tab, directly beneath the main table, separated by `marginTop: '1.5rem'`
(spacing token `md`+, matching the existing section-gap rhythm on this page).

**Structure:** `Most-Subscribed Usual Shifts` heading (Heading role, 18px/600, matches `15-UI-SPEC.md`
§3's "Suggested Library" heading treatment exactly), the subtext line directly beneath it (`fontSize:
'0.8rem', color: '#6b7280', marginBottom: '0.75rem'`), then a two-column table:

`Shift Template` | `Agents (Usual Shift)` — one row per template with ≥1 subscribing agent, sorted

judgment the requirement deliberately does not make (DRFT-04's explicit "no mitigation" framing).
