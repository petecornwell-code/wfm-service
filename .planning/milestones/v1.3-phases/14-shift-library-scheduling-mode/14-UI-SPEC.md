# Phase 14 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Primary surface:** `frontend/src/pages/ShiftLibrary.tsx` (new page, desk-scoped, mirroring
`Specializations.tsx`). **Secondary surface:** `frontend/src/pages/DeskManagement.tsx` (gains one
read-only column).
**Nature of this phase:** a new admin CRUD page plus a mode toggle and a validation panel, built
entirely from patterns already proven on four existing pages — not a new visual language.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none |
| Preset | not applicable |
| Component library | none — hand-rolled, inline `style={{...}}` objects (React 19, hooks-only) |
| Icon library | none — unicode glyphs only (✓, ⚠, ▸/▾ where a chevron is needed — matches the existing `↑`/`↓` sort indicators and `«`/`‹`/`›`/`»` pagination glyphs already in the codebase) |
| Font | `system-ui, -apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, sans-serif` (`frontend/src/index.css:2`) |

**No design system was initialized for this phase — confirmed, not skipped.** `components.json` is
absent; no `tailwind.config.*`/`postcss.config.*` exists anywhere in `frontend/`; `package.json` has
zero UI-library dependencies (React 19 + React Router 7 only, verified this session). Every one of
the 13+ existing pages (`Specializations.tsx`, `DeskManagement.tsx`, `DeskAgents.tsx`,
`ClientManagement.tsx`, etc.) uses 100% inline `style` objects against the small shared token set in
`frontend/src/index.css`. Phase 13's own UI-SPEC recorded this exact reasoning and it still holds:
introducing shadcn for one new page would make `ShiftLibrary.tsx` look and behave differently from
the `Specializations.tsx` page it is explicitly built to mirror (14-CONTEXT.md D-14), on a phase whose
own research confirms zero new dependencies are needed (`14-RESEARCH.md` § Standard Stack). **Every
rule below extends the existing hand-rolled token set — nothing new is invented that a future page
couldn't reuse.**

`config.json` records `mode: "yolo"` for this project (fully autonomous phase execution) — the
shadcn-initialization gate's interactive prompt is answered here by the codebase's own five-phase
precedent rather than a live question: keep `Tool: none`.

## Color

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#f8f9fa` | Page background (unchanged, `index.css:6`) |
| Secondary (30%) | `#fff` / `#f3f4f6` | Table/panel surface / table header row (unchanged) — the coverage panel and the mode-toggle section both use `#fff` so all three stacked sections read as one page, not three competing cards |
| Accent (10%) | `#3b82f6` | Reserved for: the "Add Shift Template" primary button, each row's inline "Save" button, the Scheduling Mode segmented control's *selected* option, and the global `input:focus`/`select:focus` outline (inherited, unchanged) |
| Destructive | `#ef4444` | **Not used by any new element in this phase** — see explicit ruling below |

**Explicit ruling on destructive red (carried forward from Phase 13, extended here — this task
explicitly asked whether the constraint still applies, so this is stated rather than assumed):**

Phase 13 forbade `#ef4444` for new elements and routed validation-error text through warning-amber
`#92400e` instead. **That constraint still applies to Phase 14, and is extended one step further:**
this phase introduces **no destructive action at all**. `Specializations.tsx` (the page D-14 mirrors
structurally) has a red "Delete" button, but `ShiftLibrary.tsx` deliberately does **not** copy it —
14-RESEARCH.md's Pattern 2 flags a hard-delete endpoint as "presently unguarded" (no FK-holding
consumer table exists yet to check against, and Phase 15/16 will add exactly such tables), and D-10
already defines the template's entire lifecycle-ending mechanism as **Retire** (setting
`effective_to`), never deletion. Retire is a fully reversible field edit — an operator can extend
`effective_to` again later — so it gets the same visual weight as any other inline edit (a plain
"Save"-style button), never `button.danger`.

The second consequence: **every new validation/refusal message in this phase — advisory (SHLB-06) or
blocking (SHLB-05/MODE-03 uncovered windows, D-02 grid misalignment, D-05 zero-demand refusal, D-13
409 conflict) — uses the same warning-amber palette below, regardless of whether it blocks a save.**
This keeps the codebase's only red-styled surface exactly where it already lives (existing
`button.danger` "Delete"/"Remove" actions on other pages, untouched by this phase), and avoids a
blocking coverage refusal visually reading as "the operator broke something" — SHLB-05's whole thesis
is that catching an uncovered window before a solve is the system working correctly, not an error the
operator caused.

**New/carried semantic roles:**

| Role | Value | Usage |
|------|-------|-------|
| Warning (amber) | bg `#fffbeb`, border `#fde68a`, text `#92400e` | Coverage panel's uncovered-windows state and no-live-demand state; SHLB-06 advisory badge/tooltip text; D-02 grid-misalignment inline error; D-13 409-conflict toast text |
| Neutral badge (gray) | bg `#e5e7eb`, text `#374151` | The "Current" era badge (D-11) — reuses the exact MANDATORY-badge palette Phase 13 established, since both are "this is the operative one" signals |
| Muted / secondary text | `#9ca3af` | "Upcoming"/"Past" era labels (plain text, not badges — see Component Specifications §1); the empty-state library copy |
| Coverage-OK text | inherits Body default (no special color) | "✓ All staffing-demand windows are covered" — deliberately NOT green. This codebase has no established "success" color token anywhere (`index.css` and every read page confirm this), and inventing one for a single sentence is out of proportion; a plain checkmark glyph plus default body color says "nothing to see here" without adding a fifth semantic color to maintain |

Accent reserved for: the "Add Shift Template" button, inline row "Save" buttons, the mode toggle's
selected state, and focus rings only — **never** for era badges, the coverage panel, or the SHLB-06
advisory glyph.

## Component Specifications

### 1. Shift Template list — table, era legibility (D-11)

Columns: `Name` (era badge/muted range shown beneath the name in the same cell), `Start–End`,
`Break` (computed window, e.g. `12:00–13:00 (60m)` — never the raw offset/duration pair; the offset
is a storage detail per D-01, not an operator-facing number), `Weekdays` (7 fixed-position chips,
valid days highlighted with Label-weight text, invalid days shown at reduced opacity — no color role
needed since it's a binary on/off per day), `Effective range` (`{from} – {to or "Present"}`), `Hours
match` (⚠ glyph + native `title` tooltip only when SHLB-06 flags the row — otherwise blank, never a
green checkmark, to avoid a fifth semantic-color role for a "nothing wrong" state on every single
row), `Actions` (`Edit`, `Retire`).

**Era legibility mechanism (resolves D-11's explicit requirement that same-name rows not look like
accidental duplicates):** rows are grouped by `name`, and within a group sorted by `effective_from`
descending — the current/most-recent era is always the top row of its group. The `Current` badge
(neutral gray, Color contract) marks the one row per name whose range covers today; `Upcoming` and
`Past` render as plain muted (`#9ca3af`) text directly beside the effective-range dates, not as
badges — this keeps exactly one colored badge per era group instead of three competing ones, so the
badge itself is the signal, not decoration repeated on every row.

### 2. Add / Edit inline form (mirrors `Specializations.tsx`'s inline row-edit pattern exactly)

Fields: `Name` (text), `Start time` / `End time` (native `<input type="time">`), `Break start time` +
`Break duration (minutes)` (native `<input type="time">` + `<input type="number">`) — **the operator
enters a wall-clock break start, not a raw offset**; the offset (`break_offset_minutes = breakStart −
startTime`) is computed client-side immediately before submit. This keeps D-01's storage model
(offset-based, zero solver freedom) intact while giving the operator the intuitive input the worked
example implies (`08:00–17:00` + break at `12:00` for `60` minutes, not "offset 240"). A live preview
line renders below the fields as the operator types: `Break {breakStart}–{breakEnd} ({duration}m),
net {X}h worked.` — this is the same "reported at definition time" thesis applied to the form itself,
not just the coverage validator.

Weekday checkboxes `Mon`…`Sun` (reuses `DeskAgents.tsx`'s `DAY_LABELS`/`DAY_ORDER` constants
verbatim — do not re-declare). `Effective from` (date, required, defaults to today for a new
template) / `Effective to` (date, optional, helper text "Leave blank for open-ended" directly below
the field).

`Save` (accent) / `Cancel` (plain) buttons, same micro-pattern as `Specializations.tsx:112-118`.
On save: D-02's grid-misalignment failure renders inline, amber text, directly below the offending
field(s) (not a toast — the operator needs to see which field is wrong while still editing). A
successful save fires the existing success toast; if SHLB-06 additionally flags the saved template as
an hours mismatch, append a second amber toast (or a second line in the same toast, planner's call)
with the advisory copy — the save itself still succeeds, per D-06's non-blocking rule.

### 3. Retire action (D-10) — not a delete, not confirm-gated

Clicking `Retire` on a row swaps that row's `Actions` cell into an inline `Effective to` date input
(defaulting to today) plus `Confirm` / `Cancel` — the same reveal-inline-then-confirm shape as the
edit form, not a modal, not a native `confirm()`. `Confirm` calls the update endpoint with the new
`effective_to`; the row then re-sorts into the group per §1 (an `Upcoming`/`Past` label may now
apply). No destructive styling anywhere in this flow (Color contract ruling above).

### 4. Coverage validation panel (D-04/D-05/D-08 — "one implementation, two callers", one panel)

Always visible below the template list, one of three states:

- **OK:** plain body text, `✓ All staffing-demand windows are covered by the current shift
  library.` — no background chrome.
- **Uncovered windows:** amber panel (bg `#fffbeb`, border `#fde68a`), heading `"{N} demand
  window(s) have no covering shift template:"`, followed by a list of `{date} {startTime}–
  {endTime}` rows. Capped at a fixed max-height with internal scroll past ~10 rows (a concrete,
  implementable rule — not left as an unverified visual claim).
- **No live demand:** same amber panel styling, single line: `"This desk has no staffing demand
  loaded. Upload staffing requirements before switching to shift-scheduled mode."`

**The panel recomputes on every template create/edit/retire** (not only at the mode-switch moment) —
this is what makes SHLB-05 genuinely "reported at definition time" rather than only discovered when
the operator later attempts the mode switch, and it is the concrete UI expression of D-08's "one
validator, two callers": the editor's own saves are one caller, the mode-switch endpoint is the
other, and both write into this same panel rather than two different UI surfaces.

### 5. Scheduling Mode toggle (D-12, D-13)

A two-option segmented control, section heading `Scheduling Mode`, options `Slot-scheduled` /
`Shift-scheduled` — selected option filled accent blue, unselected plain/outline (Color contract).

- **Slot → Shift:** clicking `Shift-scheduled` immediately calls the switch endpoint — **no
  `confirm()`, no intermediate step** (D-12 applies to the direction it doesn't gate; the *gate*
  itself is the endpoint's own validation, not a client-side dialog). On success, the toggle moves.
  On a 400 (coverage failure), the toggle visually snaps back to `Slot-scheduled` and the Coverage
  panel (§4) updates in place with the failure detail — no separate error surface duplicates that
  list. On a 409 (D-13, `RUNNING` solve), the toggle snaps back and a toast shows the conflict copy
  (a one-line fact, not a coverage list — the toast is the right size for it).
- **Shift → Slot:** clicking `Slot-scheduled` switches immediately, unconditionally — **freely
  reversible, ungated, no confirm()** (D-12, verbatim). Both options disable during the in-flight
  request (existing boolean-flag convention); no spinner glyph.

### 6. `DeskManagement.tsx` — read-only mode column

New `Scheduling Mode` column, positioned after `Default Hours/Day` and before `Actions`. Renders
`Slot` or `Shift` as plain text (the `Current`-badge gray treatment is available but not required —
planner's call; either reads as clearly non-interactive). **Never editable from this page** — D-14's
whole reason for putting the toggle on `ShiftLibrary.tsx` instead is that a refusal needs to sit next
to the library an operator would edit to fix it; this column exists only so the desk list keeps
telling the truth about a desk's current mode at a glance.
