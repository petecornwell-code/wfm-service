Run the following AWS CLI verification commands. All commands use `--region eu-west-2`.

**INFRA-03: RDS reachable from ECS (security group rule)**

Step 1 — Get the ECS security group ID:
```
ECS_SG=$(aws ec2 describe-security-groups --region eu-west-2 --filters "Name=tag:Name,Values=wfm-service-ecs-sg" --query 'SecurityGroups[0].GroupId' --output text)
echo "ECS SG: $ECS_SG"
```

Step 2 — Get the RDS security group and verify port 5432 ingress from ECS SG:
```
aws ec2 describe-security-groups --region eu-west-2 --filters "Name=tag:Name,Values=wfm-service-rds-sg" --query "SecurityGroups[0].IpPermissions[?FromPort==\`5432\`]" --output json
```
Expected: JSON array with one entry containing `UserIdGroupPairs[0].GroupId` equal to the ECS_SG value from Step 1. This proves ECS tasks can reach RDS on port 5432.

Step 3 — Verify RDS instance is in `available` state:
```
aws rds describe-db-instances --region eu-west-2 --query "DBInstances[?DBInstanceIdentifier==\`wfm-service-dev\`].{Status:DBInstanceStatus,Endpoint:Endpoint.Address,Port:Endpoint.Port}" --output table
```
Expected: Status = `available`, Port = `5432`, Endpoint = a `*.eu-west-2.rds.amazonaws.com` address.

**INFRA-04: Database password in Secrets Manager**

Step 4 — Verify the secret exists:
```
aws secretsmanager describe-secret --secret-id "wfm-service/dev/db-password" --region eu-west-2 --query '{Name:Name,ARN:ARN,VersionsExist:length(VersionIdsToStages)}' --output table
```
Expected: Name = `wfm-service/dev/db-password`, ARN present, VersionsExist >= 1.

Step 5 — Verify ECS task definition references the secret (not plaintext):
```
TASK_DEF=$(aws ecs describe-task-definition --task-definition wfm-service-dev --region eu-west-2 --query 'taskDefinition.containerDefinitions[0].secrets' --output json)
echo "$TASK_DEF"
```
Expected: JSON array containing an object with `"name": "SPRING_DATASOURCE_PASSWORD"` and `"valueFrom"` containing the Secrets Manager ARN (not a plaintext password).

Step 6 — Verify the task definition does NOT have the password in plaintext environment vars:
```
aws ecs describe-task-definition --task-definition wfm-service-dev --region eu-west-2 --query 'taskDefinition.containerDefinitions[0].environment[?name==`SPRING_DATASOURCE_PASSWORD`]' --output json
```
Expected: Empty array `[]` — the password must NOT be in the `environment` block, only in `secrets`.

Record all verification results (pass/fail with evidence) in the SUMMARY.

  </verify>

**INFRA-05: Flyway migration readiness verification**

Flyway runs automatically when the Spring Boot app starts (Phase 4). In Phase 3, we can only verify the PRECONDITIONS are in place.

Step 1 — Verify migration files exist (24 expected):
```
ls -1 src/main/resources/db/migration/V*.sql | wc -l
```
Expected: 24

Step 2 — Verify ECS task definition has the database connection URL:
```
aws ecs describe-task-definition --task-definition wfm-service-dev --region eu-west-2 --query 'taskDefinition.containerDefinitions[0].environment[?name==`SPRING_DATASOURCE_URL`].value' --output text
```
Expected: A JDBC URL like `jdbc:postgresql://wfm-service-dev.*.eu-west-2.rds.amazonaws.com:5432/wfm` — this is how the Spring Boot app (and Flyway) connects to the database.

Step 3 — Verify the RDS parameter group is applied (needed for pgvector in V24):
```
aws rds describe-db-instances --region eu-west-2 --query "DBInstances[?DBInstanceIdentifier==\`wfm-service-dev\`].DBParameterGroups[0].{Name:DBParameterGroupName,Status:ParameterApplyStatus}" --output table
```
Expected: Name matches `wfm-service-*` (custom parameter group), Status = `in-sync`.

Step 4 — Verify CloudWatch log group exists (where Flyway output will appear):
```
aws logs describe-log-groups --log-group-name-prefix "/ecs/wfm-service" --region eu-west-2 --query "logGroups[0].logGroupName" --output text
```
Expected: `/ecs/wfm-service-dev` (the ECS task logs go here; Flyway migration output will appear here when a task starts in Phase 4).
