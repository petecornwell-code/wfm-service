## P-02 — Gap (a) is closed by hydrating on read, NOT by persisting the counts at accept time

`22-VERIFICATION.md`'s `missing:` item 1 offers both routes and asks the plan to state which it
takes and why. **This plan hydrates on read.** Three measured reasons, in order of weight:

**1. Persisting would introduce a NEW silent disagreement, which is worse than the one it fixes.**
`buildRestWaiverDisclosure` reads `schedule.getAgentRestWaivers()`, and `loadSnapshotData` populates
that from the LIVE `agent_rest_waiver` table — `findByTenantIdAndDeskIdAndDateBetween` over the
schedule's period, not a per-schedule waiver snapshot. So an accepted schedule's disclosure already
re-derives against today's waiver rows by design. A persisted count would freeze at accept time
while the detail response's `applied`/`unused` lists continue to move: add or delete one waiver
after accept and the badge would read "2 applied" above a tab listing three rows. That is exactly
the silent-disagreement class D-08's shared predicate and `RestWaiverPredicateGuardTest` exist to
prevent, and it would be a defect *created* by the fix.

**2. Persisting is `one-way`; hydrating is `reversible`.** A persisted count means two mapped
columns on `schedule` plus a Flyway migration (V56) against `dev` — which is the live system with
real tenant data, and at least one live desk already holds an accepted schedule. Undoing it needs a
second migration. Hydrating on read adds no column, no migration and no persisted state.
**Explicit reversibility rating, as asked: the rejected persist route is `one-way`; the chosen
hydrate-on-read route is `reversible`.** Because the chosen route is not `one-way`, no
`checkpoint:decision` task is inserted in this plan.

**3. The cost objection against hydration is answerable, and the answer is structural.** The
verification rightly flags that a per-row `loadSnapshotData` in `listSchedules` would be an N+1,
and that polling cost on this service is a real operational concern (~4 MB detail payload competing
with the solver for two cores). This plan does not call `loadSnapshotData` at all. Its cost is
bounded by three gates, in this order, and each one is independently asserted by a test:

- **Gate 1 — the snapshotted value.** No waiver query is issued for a schedule whose
  `minimumRestMinutes` is null. `NULL` is the default and `Desk.schedulingMode` defaults to `SLOT`,
  so on the overwhelming majority of desks `listSchedules` issues *zero* extra queries, exactly as
  today.
- **Gate 2 — one batched waiver query per page.** For the DB-sourced schedules that pass gate 1,
  `listSchedules` issues ONE desk-wide, date-ranged waiver query spanning
  `min(periodStartDate)`..`max(periodEndDate)` across them, and partitions the result in memory.
  Never one query per row.
- **Gate 3 — no spans unless a waiver exists.** `buildRestWaiverDisclosure` iterates ONLY over
  `schedule.getAgentRestWaivers()`. A schedule with no in-period waiver therefore needs no span data
  at all: `(empty, empty)` is the correct answer, not a degraded one. Only a schedule that actually
  has an in-period waiver loads spans, and then only for the business dates those waivers reference
  — `{D, D-1} ∩ [periodStartDate, periodEndDate]` over the distinct waiver dates — through the
  per-business-date finders plan 22-06 already built. The bound is `2 × distinct waiver dates`
  single-date reads for that one schedule, never the whole-schedule read whose cost
  `AgentAssignmentRepository`'s own javadoc measures at six figures of rows on a large SLOT desk.

Waivers are exceptional by construction (D-09 calls them "the genuinely exceptional ones"), so in
practice gate 3 almost never opens. Where it does, the cost is a handful of indexed single-date
reads on a page load that is not polled.

## P-03 — A relations-fetching waiver finder is a correctness precondition, not an optimisation

`src/main/resources/application.yml` sets `spring.jpa.open-in-view: false` and
`AgentRestWaiver.agent` is `@ManyToOne(fetch = FetchType.LAZY)`.
`buildRestWaiverDisclosure` reads `waiver.getAgent().getName()`. `listSchedules` and
`getScheduleSummary` carry no `@Transactional` annotation, so initialising that proxy outside a
session throws `LazyInitializationException` — a 500 on the schedule list for any desk that has a
waiver, not a wrong number. The existing non-fetching finder is therefore not reusable on these
paths. One new `@Query` finder with `JOIN FETCH w.agent` serves both the new hydration helper and
`loadSnapshotData`, so the disclosure's waiver input is loaded exactly one way on every path.

## P-04 — WR-02's fix is a deleted duplicate plus a registry-backed structural guard

The reviewer's own framing is that a parity test is the wrong instrument when this same phase built
`RestWaiverPredicateGuardTest` for the analogous risk. So: delete
`ScheduleController.toSummary` outright and delegate, then add a guard that parses a registry and
asserts set equality on the production classes containing a `ScheduleSummary` construction — the
`bday-join-guard.md` / `rest-waiver-predicate-guard.md` format, with
`MidnightTimeArithmeticGuardTest`'s comment-stripping scan technique. Set equality only, never
subset or containment: widening it to `isSubsetOf` or a bare `contains` converts the guard into
decoration, as both precedents' own javadocs warn.

**Reversibility: `costly`.** Removing two parameters from a public `@RestController` constructor is
a compiler-forced migration with two test call sites; undo is mechanical but touches the same four
files. Taken anyway, because an unused injected dependency left behind to avoid the churn is debt a
reviewer would flag next pass.
