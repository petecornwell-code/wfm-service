skipped step — recorded here so `gsd-ui-checker` sees the reasoning rather than a silent omission.

## Spacing Scale

This phase introduces no new spacing convention. It reuses the project's existing scale exactly,
extracted from `src/index.css` and the inline `style={{}}` values already in `DeskManagement.tsx`,
`AgentExceptions.tsx` and `ScheduleResults.tsx`:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (`0.25rem`) | Icon-triangle-to-text gaps, badge internal padding |
| sm | 8px (`0.5rem`) | Compact element spacing — form-row gaps, button groups |
| md | 16px (`1rem`) | Default element spacing — card padding, page margins |
| lg | 24px (`1.5rem`) | Section-level padding (rare; most sections use `md`) |
| xl | 32px (`2rem`) | Page padding (`.main-content`) |

Exceptions: **12px (`0.75rem`) appears throughout** as a pre-existing, non-8-point value — card
padding (`AgentExceptions.tsx`'s "Add Exception" box), table-ish cell padding
(`th, td { padding: 0.75rem 1rem }` in `index.css`), and several `marginBottom` values on this
page's own existing sections. This phase does not introduce a new exception; it reuses the
existing one. Every new element this phase adds (the desk table column, the Rest Waivers section,
the Rest Waivers tab) must pick from the table above or from this one pre-existing 12px value — no
new off-scale number. **12px is the only sanctioned off-standard-set value for Phase 22.** No
further exception may be introduced at planning or implementation time without a new revision of
this UI-SPEC.

### 1. Desk configuration — `frontend/src/pages/DeskManagement.tsx` (REST-01, REST-04)

A sixth table column, inserted between the existing "Day Start" and "Actions" columns (per
22-CONTEXT D-04, which names this exact file and table).

**Visual anchor:** the eye continues left-to-right along the existing table row exactly as it does
today; the new column introduces no new color, weight, or size, so no competing anchor is added —
"Actions" (the row's buttons) remains the rightmost, highest-contrast element on the row, unchanged
from today.

- **Header text:** `Min Rest (hrs)` — unit stated in the header, matching the existing `Default
  Hours/Day` column's convention of naming the unit in the header rather than per cell.
- **Read-mode cell:** the value in hours (e.g. `11`, `10.5`), or `—` when unset — identical dash
  convention to the Description column's `{desk.description || '—'}`.
- **Edit-mode cell:** `<input type="number" step="0.25" min="0" style={{ width: '90px' }} />`,
  sized like the existing `editHours` input (`width: '80px'`) one column over. Empty input = unset
  (`NULL` on save), not `0` — `0` is a legal, meaningfully different value (a desk that enforces
  "shifts may touch but not overlap") from "no minimum configured at all" (REST-04's "unaffected,
  correctly reflecting that there is no legal minimum being silently assumed" — `FEATURES.md:150`).
- **Validation:** inline amber (`#92400e`) text beneath the input, shown only when the typed value
  is negative or `≥ 24` — see Copywriting Contract for the exact string. This is a client-side
  guess at D-05's bound (not yet fixed at planning time); the authoritative refusal is whatever the
  server returns, surfaced through the existing `getErrorMessage`/`showToast('error', ...)` path
  this page already uses for the day-start save.
- **Save mechanics:** follows the exact pattern `editDayStart` already establishes in this file's
  `handleUpdate` — a second, independent `PUT` call (to the new `/desks/{deskId}/minimum-rest`
  endpoint) fired only when the value actually changed from `original`, after the main desk-fields
  `PUT` succeeds. No new confirm dialog (matches the day-start precedent, Phase 14 D-12's reasoning
  against training operators to click through confirms).
- **No lock/disable state is needed for this field.** Unlike `dayStart`, nothing in 22-CONTEXT
  describes an accepted-schedule lock on `minimumRestMinutes` — D-14 explicitly declined mirroring
  `setDayStart`'s unconditional refusal here, reasoning that rest is ordinary desk policy an
  operator may change mid-quarter. If planning reverses that, the lock-disclosure pattern already
  built for `dayStart` (`dayStartLockExplanation`, the disabled `<input readOnly disabled>` plus
  muted explanatory text beneath it) is the one to copy, not a new mechanism.

### 2. Waiver entry — `frontend/src/pages/AgentExceptions.tsx` (REST-06)

**Discretion resolved: this extends the existing Agent Exceptions page with a new section, rather
than a new route.** The page is already scoped by `deskId`/`agentId` URL params exactly as REST-06
needs ("one agent, one business date"); a second route would duplicate that scoping for no
benefit, and 22-CONTEXT D-07 is explicit that REST-06's "existing per-agent exception mechanism"
means *this surface*, not the `agent_exception` table.

New section, placed **below** the existing exceptions table and "Save All" button, inside its own
card (`background: '#fff', padding: '1rem', borderRadius: '8px'`, matching the "Add Exception"
box above it):

**Visual anchor:** the page's primary anchor stays the existing "Add Exception" card at the top,
unchanged — this new card is a same-weight sibling beneath it, not a competing focal point. Within
the new card, the accent-blue "Add Waiver" button is the only accent-colored element, so it is the
one thing on this card that pulls the eye, matching how "Add" already does on the card above it.

- **Heading:** `<h3>Rest Waivers</h3>`
- **Helper text**, one muted line (`#6b7280`, `0.85rem`) beneath the heading, explaining D-06's
  waiver direction in operator language (never the raw "waives rest coming into D" phrasing):
  *"Waives the desk's minimum rest requirement for this agent on one date — the agent may start
  early on the date you pick."*
- **Add form:** `<input type="date">` + `<input placeholder="Reason (required)">` + `button.primary`
  labeled **"Add Waiver"** — same row layout as the existing "Add Exception" form directly above
  (`display: flex, gap: 0.5rem, flexWrap: wrap, alignItems: center`).
- **Interaction model — deliberately different from the Exceptions table above it, and the
  difference must not be "corrected" at implementation time:** the existing Exceptions table is
  local-optimistic-then-batch-`Save All`, because an operator typically edits several dates for one
  agent at once. A rest waiver is the opposite shape — rare, single-row, high-attributability
  (mandatory reason) — so **Add and Delete each call the server immediately** (`POST` on Add,
  `DELETE` on Delete), with no batch "Save" step and no local-only pending state. `showToast`
  confirms each immediate action ("Waiver added" / "Waiver removed"), matching the toast-per-action
  pattern this file already uses for exceptions' own create/delete.
- **Table columns:** `Date | Reason | Actions`. No "Standard Hours"/"Override Hours" columns —
  D-07 is explicit a rest waiver carries no hours value; adding one would silently resurrect the
  rejected "required hours plus a flag" design.
- **Day-off dimming (optional, non-blocking advisory only):** this component already loads
  `daysOff` for the agent and already dims exception rows on a day-off date (`isDayOff` → muted
  row background `#f3f4f6`, text `#9ca3af`, `(day off)` suffix). Reusing that exact same dimming
  for a waiver row whose date is a day off is a legitimate, low-cost advisory consistent with
  D-09's "a waiver that waives nothing is inert" — **but it must never block the Add action**;
  D-09 explicitly rejected refusing a waiver at save time even for the knowably-inert day-off case.
- **Delete:** no confirmation dialog — see Copywriting Contract.

### 3. Disclosure — `frontend/src/pages/ScheduleResults.tsx` (REST-07)

Two additions, matching D-13 (fields, computed deterministically, never from `explain()`) and D-15
(a summary-level count plus a detail-level section).

**Visual anchor:** the header row's existing anchor — Status / Feasible — is untouched and remains
first-read; the new badge sits last in that row, same muted treatment as the adjacent "Feasible
after…" text, so it reads as an incremental fact appended to the row, not a new focal point. Inside
the new tab, the "Applied" sub-table (success-green) sits above "Unused" (neutral-grey) specifically
so the positive case reads first, matching the existing pattern of ordering a page's own good news
before its informational notes.

**(a) Header badge — summary-level, visible even while `RUNNING`.** In the existing header `<div>`
(the row already carrying Status / Desk / Period / Score / Feasible), add one more `<span>`,
rendered **only when the schedule's snapshotted `minimumRestMinutes` is non-null** (hidden entirely
for a desk that never configured rest — REST-04's "solves exactly as today" extends to the display,
not just the solve):

```
Rest Waivers: {appliedCount} applied, {unusedCount} unused
```

Both counts render even at zero — see the zero-one-many row above; this is deliberate, so an
operator can tell "rest is enforced and nothing needed waiving" apart from "rest isn't configured
at all," which hiding-at-zero would conflate. This field must be sourced from the 2-second
`/summary` poll merge (the same `setSchedule(prev => ({ ...prev, status, score, feasible,
feasibleAt }))` merge block), not only from the 30-second detail fetch — D-13 puts the counts on
`/summary` specifically so they are live during a running solve, and a badge that only updated on
the slow path would silently lag the number it most needs to be honest about.

Make the badge clickable (`cursor: pointer`, switches `activeTab` to `'restWaivers'`) — a free,
low-cost affordance, not a new interaction pattern (the existing tab buttons already use the same
click-to-switch mechanic).

**(b) New tab — detail-level, full disclosure.** Insert `'restWaivers'` into the existing tab union
(`'staffing' | 'agents' | 'allocation' | 'preferences' | 'drift' | 'violations' | 'pto'`),
positioned immediately after `'violations'` and before `'pto'` — it is a compliance-adjacent view,
grouped with Violations rather than with PTO. Tab label: **"Rest Waivers"**.

Tab content, in the same `<div style={{ background: '#fff', padding: '1rem', borderRadius: '8px',
overflowX: 'auto' }}>` wrapper every other tab uses:

- Empty states: see Copywriting Contract (two distinct cases).
- When populated, **two sub-tables under their own `<h4>` (or equivalent) sub-headings, "Applied"
  and "Unused"** — D-09's own words are "two sections," not one filterable table, so the layout
  takes that literally rather than reusing `ViolationsTab`'s all/HARD/SOFT filter-chip pattern.
- **Column shape, both sub-tables** (render whichever of D-13's fields the DTO actually carries;
  any absent field renders `—`, the same null convention used throughout this file):

  | Agent | Prior shift (date + end) | Next shift (date + start) | Required gap | Measured gap | Reason |
  |---|---|---|---|---|---|

  Gaps render as decimal hours with one decimal place and an `h` suffix (e.g. `10.5h`) — chosen
  over a bare number specifically because this row sits beside two date-and-clock-time columns,
  where an unlabeled number could be misread as a time.
- **Status treatment:** the "Applied" sub-table's rows (or a per-row badge, if a single combined
  table is what the DTO shape naturally produces) use the **success** treatment (`#15803d` /
  `#f0fdf4`) from the Color section; "Unused" rows use the **neutral/muted** treatment (`#6b7280` /
  `#f3f4f6`) — not amber, not red. An unused waiver is information, not a warning; D-09's own
  framing is "reported as unused," never "flagged."
- Table font-size `0.85rem`, matching `ViolationsTab`'s (and every other tab's) existing
  `<table style={{ fontSize: '0.85rem' }}>` convention exactly — an inherited citation, not a new
  size; see Typography above.
