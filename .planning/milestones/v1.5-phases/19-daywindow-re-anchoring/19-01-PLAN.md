<planner_decisions>
Four decisions this plan makes that `19-CONTEXT.md` and `19-RESEARCH.md` leave open. They bind every
later plan in the phase.

**P-01 — `ScheduleConstraintProvider`'s `ifExists`-gated constraints keep an allowlisted midnight
anchor; SOLV-01 owns their removal.** The pattern mapper flagged `breakBlockedWindow`. Verified this
session, the problem is larger: 21 of the file's 23 `DayWindow` references sit inside constraints
gated by `.ifExists(ScheduleConfig.class, filtering(...))`, or inside helpers reached only from
them, and `ifExists` never adds its class to the output tuple. Raising those streams to carry `cfg`
is not possible — `exactlyOneBreak`, `breakBlockedWindow` and `honourPreferredBreakTime` are already
Quad, and the file's own javadoc (line 265, and `exactlyOneBreak`'s and `honourPreferredBreakTime`'s)
records that Timefold 1.16.0 has no Penta stream, which is exactly why `ifExists` was used there in
the first place. Every alternative — adding an anchor to `AgentDayConfig`, restructuring the
`groupBy` chain — is a solver problem-fact change, which is SOLV-01's stated deliverable and is what
the roadmap's "do not combine it with the join re-point that follows" forbids. This is a dependency
conflict, not a difficulty judgement. Only the two sites where `cfg` IS in the tuple —
`shiftEnvelopeCompliance` (the tracer, plan 19-03) and `breakClustering` (plan 19-04) — consume the
real anchor this phase. `19-CONTEXT.md` D-10 rejected "deferring the solver channel"; this does not
defer it — the channel is built here and consumed in plan 19-03 — it allowlists the subset Timefold's arity cap makes
unreachable. See plan 19-07 for the single named constant and its one allowlist entry.

**P-02 — the anchor-source rule, applied in this order at every call site in the phase.**
(1) the method already receives a `LocalTime dayStart` — bind it; (2) the class holds a
`DeskRepository` and the method has a `deskId` — load the `Desk` and bind `getDayStart()`; (3) the
method receives a `Schedule` — bind `getScheduleConfig().dayStart()`; (4) the lambda has `cfg` in
its tuple — bind `cfg.dayStart()`; (5) none of those, but a caller one level up satisfies 1–4 — add
a `DayWindow window` parameter and let the compiler propagate; (6) propagation would reach a
controller or a `main` — bind `LocalTime.MIDNIGHT` and add a D-07 allowlist entry. Rule 5 is what
keeps rule 6 rare; rule 6 is never the first answer.

**P-03 — `ShiftTemplateController` is served by the service, not given a `DeskRepository`.**
The controller (confirmed by a full constructor read) holds only `ShiftTemplateService` and
`ShiftTemplateBreakBandRepository`. `ShiftTemplateService` already holds `DeskRepository`.
Plan 19-04 adds a public `DayWindow dayWindowFor(UUID deskId)` to that service; the controller calls
it once per endpoint and passes the object down. No `LocalTime` crosses the controller boundary,
and D-08's rejection of controller-to-solver threading is untouched — nothing here reaches the
solver.

**P-04 — `Schedule.dayStart` is a persisted column, added by V54.** `Schedule` is a JPA `@Entity`
on `@Table(name = "schedule")`, and `MigrationEntityConsistencyTest` reconciles every
`@Column`-mapped `Schedule` field against the effective migration column map — so a `@Column` field
with no migration fails a Phase 18 guard that criterion 4 requires stay green. A `@Transient` field
is worse: it reads `null` on any `Schedule` re-hydrated from the database, which NPEs `anchoredAt`
on exactly the `ScheduleOutputService` path D-08 names. A `Schedule` row is already a point-in-time
snapshot of its solve inputs — `start_time`, `end_time` and `scheduling_mode` are snapshotted the
same way — so this is the established shape, not a second copy of desk state. Note `STATE.md`'s
"next migration is V40" is a stale v1.3-era line; the real head is V53.

**P-05 — `ScheduleDetailResponse` carries the anchor too, and it lands in the same additive commit.**
`ScheduleExportService` receives only that DTO, never a `Schedule` (confirmed: `ScheduleController`
calls `exportToExcel(detail, daysOff)`), and the DTO already carries `startTime`, `endTime`,
`incrementMinutes` and `schedulingMode` as snapshots of the same solve inputs. Adding `dayStart`
beside them is the established shape and avoids the alternative — threading a window from
`ScheduleController`, which would need a desk source the controller does not have. It lands in the
additive commit rather than a re-anchoring one because `ScheduleDetailResponse` and `ScheduleService`
are not `DayWindow` call sites, and criterion 5 confines the re-anchoring range to files that are.

**P-06 — criterion 5 is checked over a commit range, not a single commit.** 83 production call
sites across 15 files cannot be one executor task, and D-10 already splits the additive plumbing
out. The check plan 19-08 runs is `git diff --name-only <V54-plumbing-sha>..<last-re-anchoring-commit-sha>`: the union of
changed files must be exactly `DayWindow` and files that reference it, and must not contain the
Phase 20 join re-point. That preserves criterion 5's actual property — the risky edit is isolated
and revertible as a unit — on the terms D-10 already set.

<assumption_delta_decision>
The `assumption-delta` detector fired with `kind: chosen` — a constant becoming a parameter.

**Noun now primary:** the anchored `DayWindow` instance. `DayWindow` stops being a static utility
whose day start is the implicit constant `00:00` and becomes a value bound to a caller-supplied
anchor, of which midnight is one instance rather than the definition.

**Decision: `promote`.** The general representation (`anchoredAt(dayStart)` plus nine instance
methods) becomes the only public surface, and the specific one (the nine midnight-implicit statics)
is demoted to a private implementation detail of the anchor-equals-midnight case (D-06, executed in
plan 19-08). This is not `add-alongside`: keeping both public is precisely the outcome D-03's
inverted reflective guard exists to prevent, because a surviving midnight-implicit static is
indistinguishable at a call site from a deliberate one and re-opens the bug class the phase closes.

**Rationale:** the codebase already carries a desk-level `Desk.dayStart` field (Phase 18), so the
anchor is real data with a real write path, not a hypothetical generalisation. Demoting rather than
duplicating is what makes criterion 1's "a missed site is a compile failure, not a judgement call"
true.

**Contract test encoding the generalised intent (suggested, not required):** `DayWindowTest`'s
inverted `DeprecationIsLive` (plan 19-08) already does this — it asserts reflectively that no public
`DayWindow` static takes a bare scheduling time, so a future convenience overload re-introducing the
midnight-implicit shape goes red without a reviewer noticing.
</assumption_delta_decision>
