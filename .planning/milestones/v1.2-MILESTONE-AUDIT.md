# Milestone v1.2 — Unified Agent Provisioning: Audit Report

## Verdict

**Phase 13 did its job.** Both critical items from the 2026-08-21 audit — I-1 (roster and export
reading the retired scalar) and F-1 (no UI surface for per-day hours) — are genuinely closed,
verified by reading current source rather than accepting SUMMARY self-report. I-4 is closed too.
The milestone's headline defect is fixed: an operator who uploads Mon–Sun contracted hours can now
see exactly what the system stored.

**The milestone still fails the audit, on an item Phase 13 was never asked to fix.**

`I-2` — the manual "Refresh from BambooHR" button bypassing the Phase 11 merge engine — was
recorded `high` on 2026-08-21 and is untouched. It is not an edge case. It is a button on the
roster page that operators are expected to click, and every click overwrites spreadsheet-sourced
identity data with BambooHR values under no precedence rule, emitting no merge report.

This is the same *class* of failure the last audit caught with I-1: a requirement verified `passed`
in its own phase, in isolation, while a second reachable entry point quietly violates it. Phase
11's verification was not wrong — the merge engine works. It is simply not the only writer.

**I-3 is mitigated, not fixed, and this report declines to call it closed.** Phase 13 added a
`confirm()` dialog naming how many MANDATORY/PTO labels a bulk apply will destroy, and added a
genuinely safe single-cell edit path. Both are real improvements. But `setContractedHours` still
deletes all seven rows and recreates them with `dayOffType` unset — the destructive write is
unchanged, and an operator who clicks through the dialog loses the labels. Warning someone before
you destroy their data is better than destroying it silently; it is not the same as not destroying
it.

## Recommended Closure

**I-2 is the decision that gates this milestone.** It was framed on 2026-08-21 as "a scoping
decision, not a defect", and that framing is still available — but it has now survived two audits
untouched, so it should be decided rather than deferred a third time. Three honest options:

1. **Route the manual refresh through `AgentMergeService`** — makes MRG-02 true on every path and
   produces a merge report for Refresh. The real fix; a small phase.
2. **Constrain the button** — e.g. refresh only fields BambooHR owns outright, leaving
   spreadsheet-sourced identity data alone. Cheaper, and removes the silent-overwrite risk without
   building report plumbing.
3. **Document the scope explicitly** — amend MRG-02 to say the precedence guarantee covers the
   upload path, and label the Refresh button so operators know it overwrites. Costs nothing in code
   but makes the limitation a stated product decision instead of an undiscovered one.

**I-3** — if the bulk destroy is genuinely intended (D-10's uniform fan-out), the remaining work is
small: preserve `dayOffType` across the delete-and-recreate, or drop the bulk action now that the
safe per-cell path exists.

**NEW-1** — either stop exporting the legacy scalar column, or have `setDayHours` keep it in sync.
