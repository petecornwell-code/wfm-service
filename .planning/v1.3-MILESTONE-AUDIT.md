### Phase 14 was `human_needed` at audit time and is now `passed`

Its three human-verification items were discharged by UAT on 2026-08-26 — the day after the report
was written — but the report was never refreshed, so the milestone carried an unverified-looking
phase for three weeks. Refreshed during this audit.

**The migration item earned its keep.** It was flagged as "the phase's single most load-bearing
unverified item", and UAT test 1 found exactly the defect it guarded: V39 declared
`valid_weekdays CHAR(7)` against an entity mapping of `varchar(7)`, so the migration applied and
backfilled correctly and *then* the application refused to boot under `ddl-auto: validate`. No test
in the 402-test suite could have caught it — the test profile disables Flyway and uses `create-drop`
against H2, so the schema comes from the entity and the migration SQL never runs. Fixed by
`9a98029`, retested clean end-to-end on Postgres 18.4. **The blind spot is closed too, not just the
instance:** Phase 15's `MigrationEntityConsistencyTest` (`d909074`, P-07) parses migration SQL
against entity mappings, so this drift class now fails the suite.

## One Cross-Phase Finding — recorded, not a gap

**Phase 15 superseded Phase 14's D-10 "no delete control" decision, and Phase 14's verification
still asserted the old state.** Found by this audit's integration check.

Phase 14 shipped retire-only and deliberately no delete path, citing the v1.2 audit's I-3 finding
on destructive controls. Phase 15's `81117e3` added a `@DeleteMapping` and a `window.confirm()`
dialog — at the operator's own request during Phase 15 UAT (`15-UAT.md:535`), because retire-only
stranded typos, duplicates and probe rows in the library forever.

**SHLB-04 is satisfied more strongly, not less.** `deleteShiftTemplate` refuses with 409 when the
template is referenced by *any* agent-day assignment **or** *any* stored usual shift, naming the
count and directing the operator to retire instead. A template that ever shaped a roster still
cannot be destroyed — and the second guard protects Phase 16 data that did not exist when D-10 was
taken. `className="danger"` remains 0; the confirm dialog "guards against the slip, not against
data loss".

This is recorded rather than filed as a gap because the requirement holds and the change was
deliberate and operator-driven. It is worth noting as a *process* observation: a later phase
changed an earlier phase's shipped decision, and nothing propagated that back, so `14-VERIFICATION.md`
asserted "no delete endpoint exists" for three weeks after one existed. Truths #5 and #22 are now
annotated there.

## Assessment

This milestone hit its goal. An agent on a shift-scheduled desk now works one shift per day drawn
from a named library, containment is a hard constraint proven against ground truth rather than
asserted, the usual shift is stored and visible in every surface that shows agent data, and drift
from it is reported per agent and date from the same distance calculation the constraint uses.

Two things stand out as genuinely well-executed. The **self-enforcing structural guards** —
`ScheduleConstraintClassificationTest`'s reflective completeness check, `UsualShiftWritePathGuardTest`'s
allowlist proven able to fail twice, `MigrationEntityConsistencyTest`'s SQL-vs-entity comparison —
mean three whole classes of regression now fail the suite instead of being caught by review
attention. And the project's honesty about what it cannot automate held: the human-verification
items were not quietly dropped, and the one that mattered most caught a real boot-blocking defect.

The debt is real but bounded, and none of it blocks archiving. The item most worth a decision before
v1.4 is **Nyquist coverage** — four phases across two milestones (10, 13, 14, 15) sit at
`status: draft`, plus Phase 16's genuine PARTIAL. That is drifting from an oversight into a pattern.
