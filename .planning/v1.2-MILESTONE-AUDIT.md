# Milestone v1.2 — Unified Agent Provisioning: Audit Report

**Audited:** 2026-08-21
**Status:** `gaps_found`

## Verdict

All 19 requirements are satisfied **by their own wording**, and every phase that was
not withdrawn verified `passed` in isolation. The milestone nonetheless fails the audit
on a **cross-phase integration gap that only appears when the phases are combined** —
precisely the failure mode this audit exists to catch.

Phase 9 made per-day `agent_day_hours` the authoritative source of contracted hours.
Phase 10's upload writes those rows. But the operator-facing roster display and Excel
export were never migrated off the retired `Agent.contractedHoursPerDay` scalar — and
the upload path actively **nulls** that scalar. The result: after an enriched upload,
the operator checking whether the upload "took" sees a flat desk-default number that has
no relationship to the Mon–Sun values they just submitted.

The solver is unaffected — it reads the per-day model through the correct choke point.
This is a reporting/verification defect, not a scheduling-correctness defect.

### I-1 (critical) — roster and export disconnected from the per-day model

`DeskAgentService.toResponse` (`DeskAgentService.java:72-74`):

```java
BigDecimal effective = a.getContractedHoursPerDay() != null
        ? a.getContractedHoursPerDay() : deskDefault;
```

`AgentDayHoursRepository` *is* injected into this class, but only used by
`setContractedHours` (`:210`) — never by the read path. Meanwhile
`DeskAssignmentUploadService.clearDesk` (`:561`) sets the scalar to `null` on every
re-import, and `grep` confirms `setContractedHoursPerDay` appears exactly once in that
service — the null. So after an enriched upload the scalar is `null` and `effective`
collapses to `deskDefault` for every agent.

Affects the roster page (`frontend/src/pages/DeskAgents.tsx:362`) and the Excel export's
"Contracted Hours Per Day" / "Effective Contracted Hours Per Day" columns
(`DeskAgentExportService.java:57-58`).

### I-2 (high) — a second, unreported identity-write path

`BambooRefreshService.persistRefreshData` (`:224-234`) writes `name`, `firstName`,
`lastName`, `email`, `department`, `jobTitle`, and `active` straight from BambooHR with
no precedence rule and no `MergeReportEntry`. It is reachable from a live
"Refresh from BambooHR" button on the same page as the upload.

MRG-01…07 are scoped to "on every upload", so this does not violate them literally — but
the milestone's headline promise ("the operator can see exactly which value came from
which source") holds only for one of two reachable paths. A spreadsheet-supplied gap-fill
can be silently overwritten with zero provenance.

It correctly leaves `agent_day_hours` alone, so D-12 and MDL-02 are not regressed.

### I-3 (medium) — Edit Hours wipes MANDATORY/PTO

`DeskAgentService.setContractedHours` (`:206-217`) deletes all seven rows and recreates
them uniformly with `dayOffType` unset. The uniform fan-out is intentional (D-10), but
the silent loss of upload-set `MANDATORY`/`PTO` labels is not surfaced to the operator.

### I-4 (low) — hardcoded specialty headers

`DeskAssignmentTemplateService.java:31-32` hardcodes `"Specialty 1"` / `"Specialty 2"`.
`EnrichedColumnLayout` offers only `specialtyIndex()` (a case-insensitive detection
regex), so there is nothing to source them from. Low practical risk — the regex accepts
these literals — but it is exactly the drift point UPL-09 and the class's own Javadoc
warn against.

## Recommended Closure

I-1 and F-1 are one fix: point the read path at the per-day model.

1. `DeskAgentService.toResponse` should resolve effective hours from `AgentDayHours`
   (ideally through the same resolution the solver uses) rather than the scalar.
2. Surface the Mon–Sun values, `MANDATORY` days and `PTO` markers somewhere in the roster
   UI — today no component in `frontend/src` references per-day hours at all.
3. Apply the same change to `DeskAgentExportService`.

I-2 is a scoping decision, not a defect: either route the manual refresh through
`AgentMergeService`, or document explicitly that the merge-report guarantee covers the
upload path only.

I-3 and I-4 are small, independent hardening items.
